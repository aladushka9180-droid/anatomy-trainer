# O14 — критерий допуска рабочего магазина ЮKassa (кандидат для решения)

Статус на v904: **не внедрено**. Живой Pro показывает «тест не подтверждён», режим «Тестовый магазин» и выключенный приём предоплаты. Настройки, секреты, платежи и production SQL не менялись.

## Что подтверждено

- Встроенный «Тестовый платёж» работает только внутри Pro, без банка и ЮKassa. Его успех доказывает UI/локальную модель, но не готовность внешнего эквайринга.
- `set_minuta_yookassa_settings` (SQL v87) проверяет роль владельца, поля и незавершённые попытки при смене режима; подтверждённого теста перед `enabled=true, environment='production'` не требует. Клиентская форма тоже отправляет это сочетание без gate и финального review.
- История `recent_attempts` ограничена 50 строками, а секреты test/production хранятся в Edge вне БД. По одному успешному test-attempt нельзя доказать актуальность реквизитов, webhook и настроек чеков. Старый UI-кандидат с одним `confirm` серверный обход не закрывает.
- `PAYMENT_FOUNDATION.md` уже задаёт последовательность изолированной проверки: тестовая БД/магазин, повтор и поддельный webhook, контрольный GET, оплата, возвраты и чеки при фискализации; лишь затем production-реквизиты и отдельное включение.

## Предлагаемый контракт при выборе автоматического допуска

Сервер отклоняет активацию рабочего магазина до связанного с **этой организацией и текущей конфигурацией** проверяемого свидетельства из изолированного контура. Свидетельство должно фиксировать успешный test-mode платёж, сверку статуса провайдером, webhook/idempotency и, если включены чеки, тест чека; повторная смена реквизитов/фискализации делает его недействительным. UI показывает только безопасные статусы шагов (без Shop ID и ключей), итоговую конфигурацию и отменяемый review. Прямой RPC без UI также обязан отказать. Отсутствующее/устаревшее/чужое свидетельство, ошибка сети и незавершённая операция — отказ без записи настроек.

Это новая схема аттестации и процесс выпуска; существующий `recent_attempts` не годится как достаточное свидетельство. Требуются отдельные тестовая миграция, сценарий отката без удаления финансового журнала, свежий бекап и конкретное разрешение на production SQL. Ни один из этих шагов пока не санкционирован.

**Единственный продуктовый выбор:** допуск рабочего магазина остаётся ручным release-gate по доказательствам из `PAYMENT_FOUNDATION.md` с отдельным подтверждением активации **или** проектируем серверно проверяемую аттестацию изолированного теста. До выбора нельзя честно помечать O14 безопасно закрытым; рабочий магазин оставляем выключенным.
