# Создание, серия и история: структурный Source-контракт

Следующий безопасный подэтап после v197: `provider-visit-create-contract.mjs` фиксирует выбранные условия и квалифицирует полный DTO результата. **Atomic managed CREATE ещё не реализован и не квалифицирован.** Формы, SQL, сервисы повторных отправок и рабочие данные не меняются; пять целевых критериев остаются 0/5.

## Снимок попытки

`captureVisitCreationEnvelope` принимает request ID от существующего владельца попытки, location ID, прежние 13 нормализованных частей canonical, выбранный `visitTerms` и явные позиции сеанса. Он использует уже подготовленный модуль условий визита, сохраняет primary rate×minutes отдельно от add-ons, считает общий итог/интервал и замораживает собственные примитивы и массивы до await.

Один визит использует тот же root request ID. Для серии вызывающая сторона передаёт заранее сохранённый список уникальных occurrence IDs: 2–24 визита, интервал 1–12 недель как в известном v79. Календарные даты вычисляются по UTC calendar days без локального DST-сдвига; политика серверного горизонта/доступности не заменяется. Модуль не создаёт IDs, не вызывает часы/сеть, не пишет storage и не владеет retry. Повторная сериализация/восстановление сохраняет тот же список.

Новый `visitCreationFingerprintCanonical` связывает root/location, прежний canonical вместе с `visitTerms`, полный сеанс, интервал и occurrence mapping. Это отдельный Source namespace для новых квалифицированных попыток. `providerBookingFingerprint`, существующий attempt reader, legacy fallback latch, request IDs и UNKNOWN-попытки не изменены. Нельзя автоматически заменять их этим форматом или создавать второй retry owner.

`restoreVisitCreationEnvelope` повторно проверяет сохранённый JSON и согласованность всех производных фактов. Формат закрыт: лишние/унаследованные поля, accessors и разреженные/декорированные массивы отклоняются. Старый UNKNOWN-объект остаётся у прежнего владельца; ошибка нового валидатора не разрешает его очищать.

## Квалификация ответа

`visitCreationReceiptMatches` принимает структурный DTO версии1 с точным canonical запроса, actor/organization/location и полным массивом occurrences. Каждая occurrence содержит свой request/date/time, уникальный booking ID, выбранные terms, полный session и отдельную revision с id/booking/actor/items/общими минутами/суммой. Пропуски, неизвестные поля вроде `status:unknown`, неполная серия, повтор booking/revision ID, иной scope/body и округление одной минуты до пяти не дают положительного результата.

DTO сообщает выбранные факты; сам predicate не доказывает атомарную транзакцию, права, исходные строки БД или доставку. Будущий writer обязан подтвердить фактический readback до формирования durable receipt. Один echo входа либо прежний booking/code/request ACK этим доказательством не являются.

Для исторических данных восстанавливаются сохранённые terms/items/revision; текущий каталог не подставляется. Это совместимость структурного снимка с прошлой датой, без допуска на создание/изменение истории. При смене услуги действует цена новой услуги; повтор/серия используют согласованную ставку исходного визита с явным изменением. Снимок сам не принимает эти бизнес-решения.

## Проверка и серверная граница

`node --test minuta-online-booking/tests/provider-visit-create-contract-test.mjs` — 11 групп: ноль/мин1, immutable inputs, серия/reload, primary/add-ons/repeat signature, изменённая идентичность, invalid bounds, повреждённый JSON/UNKNOWN, точный readback, прошлый DTO и два review-regression. Последние две группы воспроизвели ошибки до исправления и прошли после него. Тест добавлен в существующий smoke CI.

Источник Pro v131 не принимает chosen terms и подтверждает только booking/code/request; v79 генерирует новые occurrence IDs при повторном вызове; v53 INSERT initializer сохраняет revision минимум5. Клиентский v153 сверяет каталоговые условия и не является Pro custom-rate writer. Эти публичные Source не устанавливают текущие managed определения/права/все triggers.

Следующий обязательный этап — квалифицированные current provider6/trigger/permissions/whole-state входы по защищённым original full-copy/restore/SQL воротам, затем один атомарный writer с точным insert-time primary/session/revision и durable полной квитанцией серии. Подмена его цепочкой create→поздний edit или отдельным дублирующим booking engine не допускается. Новый SQL, применение, формы и actual browser/PWA остаются открытыми. Прежние edit v197/local16/native4/CI15 относятся к своему неизменённому head5751af8f; здесь проверяется только новая Source-дельта.
