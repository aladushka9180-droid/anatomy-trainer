# Индивидуальный тариф: кандидат атомарного редактирования

Source-этап draft PR136. Миграция `supabase/migrations/20261027211342_provider_visit_terms_v197.sql` добавляет отдельные RPC для **одного будущего scheduled-визита** с уже согласованной поминутной primary-позицией. Действующие формы, `provider.js`, старые RPC создания/сеанса и общий выпуск PR134 не меняются. Целевая приёмка функции остаётся **0/5**.

## Контракт

1. `get_minuta_visit_terms_v197(booking)` возвращает полный снимок владельца/организации/услуги, даты/времени/статуса, ставки, общих минут/суммы и позиций. Digest включает все ревизии, включая добавленную позже ревизию с более старым timestamp. Снимок — условие последующей записи, не доказательство готовности интерфейса.
2. `save_minuta_visit_terms_v197(request_id, booking, expected, minute_rate, primary_minutes)` принимает целые рубли 0–1 000 000 и primary-минуты 1–480; сумма primary ограничена 1 000 000. Итог включает прежние add-ons, время — только add-ons с `extends_duration`. Ставка не извлекается из общего итога и не пишет в каталог услуг.
3. Один transaction сравнивает текущий снимок с `expected`, меняет primary и booking, добавляет exact ревизию, проверяет результат и только затем сохраняет неизменяемую квитанцию. Идентичный retry возвращает ту же revision; другой actor/body с тем же request ID отклоняется. Дополнительно возвращаются текущий снимок и `currentMatchesReceipt`: старый успех не означает, что визит с тех пор не менялся. Request ID создания нельзя использовать для редактирования.
4. Изменение ставки при прежнем интервале не включает `duration_minutes` в UPDATE и не запускает `UPDATE OF duration_minutes`. При изменении длительности обычные триггеры booking продолжают действовать. Ошибка/несовпадение readback откатывает всю операцию. Сохраняются identity и все прочие поля primary, полные add-on rows и соседние поля booking.

## Доступ и совместимость

RPC проверяют `auth.uid()` и владельца каждой записи; callable только `authenticated`. Внутренний snapshot не выдан клиентам. Новая receipt-таблица принадлежит `postgres`, имеет RLS+FORCE без policies, без прямых grants клиентам/`service_role`; обе публичные функции используют закреплённый пустой search_path. Отсутствие FK к booking сохраняет существующий порядок удаления; квитанция продолжает обозначать совершённую попытку после удаления визита.

Смена цены каталога не меняет сохранённую ставку. Каталоговая поминутная услуга либо точное продолжение ранее записанного снимка квалифицируют режим. Receipt продолжает квалифицировать неизменённую service/session lineage после смены каталогового режима; A→B→A через старый writer добавляет ревизии и прежний режим не возрождает. Неоднозначные старые данные, чужие позиции, итог/primary mismatch, прошлый/завершённый визит, блок или отмена отклоняются.

Локальная проверка использует опубликованный Source v53/v156, настоящий PG SHA-256 и синтетические auth claims/данные. Старая `save_booking_session(uuid,jsonb)` сохраняет исходный `prosrc`; её предел 5–480 не меняется. Только CHECK ревизий расширяется с 5–480 до 1–480 для exact одной минуты нового API.

Блокировки: request19701 → booking7302 → organization7100 → performer/day0 → booking row NOWAIT. Старый v156 берёт row раньше дневной блокировки; NOWAIT возвращает `40001 visit_terms_booking_busy`, освобождая блокировки нового transaction. Клиент должен показать конфликт/получить свежий снимок; безусловный новый request ID или смена `expected` в старой попытке запрещены.

## Откат

`minuta-online-booking/recovery/rollback-provider-visit-terms-v197.sql` допускает только чистый откат **до первой записи v197**. Он закрепляет SHA исходников новых функций, проверяет owner/ACL/search_path и receipt-схему, берёт NOWAIT locks, не использует CASCADE и восстанавливает CHECK 5–480. Существующие bookings/items/revisions и старые RPC не переписываются.

Любая receipt либо revision короче пяти минут даёт `v197_rollback_data_retention_hold`; изменение функций/прав/таблицы также останавливает откат. После появления данных нужен отдельный согласованный план сохранения данных и действующие restore/SQL ворота. Удалять receipts/историю для обхода HOLD запрещено.

## Проверка и границы

- Pure module: 8 групп тестов расчёта/снимка/черновика/fingerprint.
- PGlite: 10 групп поведения RPC и 6 групп rollback/reapply/retention/drift на одноразовых fixture.
- Workflow `Visit terms atomic edit contract`: отдельный PostgreSQL 17 service, четыре native проверки — clean rollback/reapply, legacy-held row без цикла ожидания, одновременный retry на двух соединениях с одной revision/receipt, retention HOLD после записи. Ниже доступен только CI loopback database `visit_terms_test`; внешняя/рабочая БД тестом не допускается.

Native CI, когда пройдёт на итоговом head, докажет именно эти проверки синтетической fixture. Это не whole-stand квалификация Supabase/RLS/всех triggers и не полная исходная копия DB/Auth/Storage. Миграция не допускается к применению до текущего защищённого full-copy/restore и точного SQL preflight. Создание, серия, past/history, UI/draft/offline wiring, общая интеграция, публикация, рабочий кабинет и установленное приложение остаются отдельными незавершёнными шагами исходных пяти критериев.
