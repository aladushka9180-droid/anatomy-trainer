# PrimeTime Pro: очередь офлайн-возможностей

Владелец очереди, изменений и последовательного выпуска — задача «Гибкое время офлайн-записи — Pro и клиент». Очередь описывает применимые сценарии, а не обещает совместимость с Гном.Гуру. Выпуск UI-аудита остаётся у его отдельного владельца; пересекающиеся файлы и полосу выпуска не занимать одновременно.

Сверка 29.09: каталог v186/v187 перенесён без старого UI на свежий `main`
в SQL-ветку `codex/pro-catalog-sql-v186-v187`, SHA `7f25681b`.
Оба isolated PostgreSQL 17 job прошли на этом SHA (`36571758657`),
booking smoke (`36571758731`) и theme/browser CI (`36571758770`) прошли.
Schema-only clone тестовой базы прошёл на `6d2c4145` (`36573493387`):
v186 → v187 → rollback → reapply и права функций проверены на пустой копии
схемы. Это не restore рабочих данных. Проверка полной восстановленной схемы
и выпуск впереди. На сайте и в рабочей
базе каталога нет. Перед интеграцией снова проверить номера на свежем `main`.
После этих проверок в четыре SQL добавлено уведомление PostgREST об обновлении
схемы. Точные новые байты `eb3e9829` прошли оба isolated PostgreSQL 17 job
`36580596630` и schema-only clone `36580596513`; полный restore с данными
и проверка живого RPC ещё не выполнены.
Для будущего restore подготовлен отдельный сетево изолированный проверочный
скрипт: CI `36589461589` проверил его на сетево изолированной копии схемы
тестовой БД с синтетическими услугой и складской позицией; обе строки
сохранились через apply/rollback/reapply. Это не проверка рабочих строк. Подключение к
защищённому workflow подготовлено в draft PR, но не опубликовано в `main`.
Запуск на закрытой копии рабочего backup требует отдельного точного разрешения.
Общий `card-states` CI PR №6 один раз упал на ожидании следующего service
worker, затем завершился успешно при однократном повторе того же SHA
(`36583898860`, attempt 2). SQL-ветка не меняет PWA-файлы; причина
неустойчивости теста не устранена и не относится к доказательству restore.

Сверка 30.09: SQL-ветка обновлена до `74f827d4` поверх `origin/main`
`fdae2ae2`; состав кандидата остаётся SQL, проверочным workflow, скриптом
восстановления и очередью. На точном SHA 19 проверок PR №6 прошли, два
`card-states` упали на ожидании будущего service worker v1037
(`36607113053`, `36607106916`); повтор только упавшего job также не прошёл.
Текущие `sw.js`, `site-update.js`, тесты и workflow этого job в ветке побайтно
совпадают с `origin/main`, где соответствующий CI прошёл (`36604221785`).
Причина расхождения на том SHA не доказана. Скрипт restore
запускается только после проверки точных SQL SHA и свежего backup run;
PostgreSQL работает без сети. На настоящей копии backup он не запускался.
Отдельное разрешение на такую проверку запрошено, ответа пока нет.

После принятого в `main` исправления PWA ветка каталога обновлена на
`daa3b792` и отправлена в draft PR №6 как `ba76b8aa`. Все 21 проверки PR,
включая оба `card-states`, прошли на этом SHA (`36657678376` и связанные
запуски). `client-url-redirect-test.mjs` прошёл; общие ресурсы PWA в ветке
совпадают с тогдашним `main`, четыре SQL blob SHA не менялись. Это снимает
прежний красный CI gate для кандидата, но не заменяет restore с данными,
разрешение на production SQL, интеграцию UI и приёмку на живом сайте.

Независимые файлы UI-черновиков сохранены в ветке
`codex/pro-offline-catalog-ui-drafts`, SHA `4af335d6`, [черновой PR №7](https://github.com/aladushka9180-droid/anatomy-trainer/pull/7).
Перечисление локальных ключей перенесено в необязательный модуль каталога;
общий `reliability.js` совпадает с main. Исходный лимит PWA-ядра сохранён:
63 файла, 3 791 893 байта; smoke `36577379260` и Linux CI компонента
`36577379111` прошли. Локальные сценарии черновиков и панели 390/760/1440
тоже прошли. Общие `provider.html/js`, SW и живой экран не подключены;
кандидат не выпущен. Отдельный theme/card CI прежнего SHA падал на ожидании
следующего worker — участок владельца UI-аудита, он не зачтён как исправленный.
После SHA `1b447e54` локально повторены только затронутые браузерные тесты:
при выходе во время записи черновик и снимок версии не восстанавливаются после
очистки. SHA `4af335d6` дополнительно распознаёт удалённый элемент и
несовпадение идемпотентного запроса как отказ без бесконечного повтора;
два затронутых браузерных теста прошли. Проверки draft PR №7 на этом SHA
завершились успешно; живой экран и PWA интеграция по-прежнему отсутствуют.
Следующий шаг — дождаться свободной полосы UI-аудита и согласовать интеграцию
с SQL PR №6, не увеличивая PWA-ядро.

## Источники и границы доказательства

- [Статья Гном.Гуру об офлайн-режиме, 02.03.2020](https://gnom.guru/ru/Blog/BPage/2518191662820853518) заявляет запись клиента, шаблон, поздравление, сотрудника, работу с ранее загруженными данными и последующую синхронизацию между устройствами. Это заявление поставщика на дату статьи, не проверка актуального приложения или всех его функций.
- [Статья Гном.Гуру об учёте материалов, 27.03.2018](https://gnom.guru/ru/Blog/BPage/2519030557121186233) описывает материалы, нормы, списание после визита, себестоимость и остатки. Она не доказывает, что каждая из этих операций сейчас доступна без сети.
- [Страница возможностей Гном.Гуру](https://gnom.guru/ru) перечисляет историю клиентов, услуги, материалы, товары, расходы/доходы и работу с нескольких устройств. Офлайн-поведение этих отдельных разделов и физическое Android-приложение нами не проверены.
- Статусы PrimeTime ниже основаны на текущем `origin/main`, проектных проверках и `MILESTONE.md`; где нет отдельного живого сценария, указано «код есть, офлайн не подтверждён». Установленная Android PWA отдельно не проверена.

## Ворота каждого этапа

Этап 1: прежнюю локальную интеграцию с SW v999 не переносить целиком: она устарела относительно живого Pro. Текущий PR №7 содержит только независимые файлы черновиков и панели; новый экран, авторизованный сценарий и PWA ещё не подключены. Пустая копия схемы тестовой БД проверена, полный restore с данными и работа с реальным складом не выполнялись. Перед выпуском нужны свежий `origin/main`, свободная полоса владельца UI-аудита, интеграция без роста PWA-ядра, CI, живые ресурсы и безопасный экранный сценарий. Для SQL v186/v187 точные границы backup/restore/rollback указаны в `minuta-online-booking/recovery/V186_V187_OFFLINE_CATALOG_RELEASE.md`; production SQL требует отдельного разрешения.

Изолированная схема и данные → проверка конфликта, повтора и потерянного ответа → браузерные сценарии 390/760/1440 и PWA без реальных записей → свежий `origin/main` и свободная полоса единственного владельца выпуска → обязательные CI/деплой → реальные ресурсы, экран и безопасное действие на рабочем сайте. Для нового production SQL отдельно требуются точное разрешение, свежий backup, isolated restore, проверка отката и preflight. Физический Android остаётся отдельной проверкой.
