# Очередь сохранения заметок, цветов и меток

Статус: реализация для согласованной публикации, не отдельное изменение production-БД.
Владелец реализации: задача «Masters отзывы», ветка `codex/offline-metadata-recovery`.
Основа: `abc09e4b`, v453. Версию ресурсов назначает владелец выпуска после свежего fetch.

## Состав

- `provider.js`: pending-маркер заметки записи записывается до запроса; исключения не теряют очередь.
- Фоновый повтор цветов, заметок записей, клиентских меток и клиентских заметок после полной синхронизации и проверки write gate.
- Клиентские заметки хранятся в отдельной очереди localStorage по аккаунту, включая пустой текст удаления.
- Фоновый повтор ждёт уже отправленные запросы; новая правка не отправляется поверх незавершённого фонового повтора. Проверки аккаунта, организации, жизненного цикла формы и карты сохранены.
- Старый ответ заметки не снимает pending новой заметки. Pending-значения видны поверх устаревшего серверного чтения.
- При неотправленных изменениях статус не утверждает полную синхронизацию.
- При отказе localStorage и сети интерфейс не утверждает сохранение локальной копии.
- Четыре существующих native harness подгружают новые реальные зависимости helpers, без удаления прежних assertions.

## Проверки

- Три узкие RED-регрессии на прежнем runtime: pending до ACK, rejected/null ответ, старый ACK поверх нового failed note.
- `tests/metadata-offline-recovery-test.mjs`: 28 VM-сценариев, транспорт/DOM синтетические; подключён через provider-ux-audit-test.
- `tests/metadata-offline-browser-test.mjs`: 6 native сценариев на 390/1280px: настоящие input/button/localStorage, повторное открытие, пустой текст, смена аккаунта. RPC синтетический.
- Существующие color revision VM 15, metadata context VM 28; native color 5, metadata 35, historical context 23, series editor 35.
- Общие provider UX, connection recovery, smoke и синтаксис provider.js.

## Границы

При отказе первичной записи очереди в localStorage новое значение не отправляется на сервер (все четыре вида metadata). Это сознательное безопасное ограничение: иначе сохранённое старое значение могло бы после reload отменить новый серверный ACK. Очереди других ключей не удаляются. Если запись pending-маркера после ACK не удалась, до отправки уже была сохранена актуальная величина, повторяется то же абсолютное значение. Quota-тесты 4/4 сначала RED, затем PASS с reopening/replay; интерфейс не обещает сохранение при отказе локального хранилища.

Второй ревьюер воспроизвёл отдельный multi-client stale snapshot на e3ad028: после подтверждения нового текста B цикл восстановления снова отправлял old B. Исправление снимает только ключи очереди и читает текущее pending-значение непосредственно перед повтором; уже подтверждённые ключи пропускаются во всех четырёх очередях. Собственный тест сначала RED на e3ad028, затем PASS; добавлены контроль последнего ещё не подтверждённого текста и отсутствие повторной отправки подтверждённых цветов/заметок записей/меток.

После независимого ревью 078294 подготовлено узкое исправление: все client_notes upsert идут через одну очередь (включая historical/create/edit/offline finalize); историческая форма обновляет отображаемый кэш только после ACK, сохраняя существующие context guards. После ожидания очереди повторно проверяется writesAllowed. RPC цвета/заметки требуют точного возвращённого TEXT, а client_notes upsert по-прежнему допускает законный PostgREST data:null/error:null. Новый ключ очереди удаляется существующей очисткой устройства при выходе/смене аккаунта. Три дополнительных VM-проверки сначала дали RED на 078294, затем PASS; независимая adversarial приёмка ещё требуется. Старые test fixtures возвращают реальные TEXT ACK вместо вымышленных true/null, утверждения сценариев не удалены.

- Не включает оплаты, бонусы, склад, возвраты, аналитику, медиа или новые SQL.
- Не разрешает новые изменения в явно read-only/offline интерфейсе. Защищает начатые сохранения и уже имеющуюся очередь; существующие write gates не ослаблены.
- Сохраняются абсолютные значения, а не операции прибавления. Это не гарантия общего порядка конкурентных правок с разных устройств/вкладок и не server exactly-once.
- Заметки и метки клиентов по-прежнему performer-scoped, как существующая таблица. Заметки/цвета записей повторяются только для загруженных записей текущей области; чужие/отсутствующие pending ID не отбрасываются молча.
- Удаление данных браузера уничтожает локальную очередь. Ошибка/переполнение localStorage не позволяет обещать её восстановление после перезагрузки.
- Реальные пользовательские записи/сообщения/платежи ради теста не менялись; authenticated production E2E не заявляется.
