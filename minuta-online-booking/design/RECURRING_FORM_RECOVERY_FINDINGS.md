# Серии записей: восстановление формы и запоздалые ответы

Статус: воспроизводимые дефекты текущего frontend-кода и план исправления;
**provider.js и SQL в рамках этой диагностики не изменялись**.
Основа: `1043106590243b7129b4aa51c2fec0c9fa031119`.
Перед реализацией владелец provider сверяет свежую интеграционную основу.

Отдельного `recurring-bookings.js` нет. UI серий встроен в `provider.js`;
серверные определения — `supabase-migration-v79.sql`. Работающий код серий,
включая охват one/following/all, уже существует; находки не означают отсутствие
этой функции и не подтверждают наблюдение дефекта в production.

## Воспроизведённые сценарии

Проверка выполнена в Node VM на **извлечённом реальном коде функций**, с маленькими
заглушками DOM и RPC. Никакие внешние RPC, уведомления или записи не выполнялись.
Счётчик побочных действий фиксировал вызовы, а не реальное серверное исполнение.

1. **Исключение при отмене оставляет заблокированную форму.** Запустить
   `cancelBookingSeries` с разрешённой записью; `db.rpc` отклоняет Promise
   `Error('network')`. Функция отклоняется наружу, кнопка остаётся disabled и
   содержит «Отменяем…». В ветке нет catch/finally.
2. **Ответ отмены закрывает другую открытую форму.** Начать cancel A, оставить
   RPC pending, открыть форму B при том же user/generation, разрешить ответ A
   с `affected:[{booking_id:'A'}]`. Зафиксированы notification(A), close(B),
   refresh и сообщение об отмене A. Проверки идентичности формы перед close нет.
3. **Исключение при переносе также блокирует кнопку.** Выполнить series-ветку
   `saveBookingChanges`; отклонить `manage_minuta_booking_series`.
   Функция отклоняется, кнопка остаётся disabled. При позднем успешном ответе
   старой формы выполняется `openBookingSheet(A)`, заменяя уже открытую B.
4. **Исключение при создании серии не восстанавливает кнопку.** Ветка
   `create_minuta_recurring_bookings` не ловит отклонённый Promise.
   При ответе старой формы она выполняет clear draft, close(B), refresh и success
   после открытия новой формы B в той же сессии.
5. **Смена сессии после основного ответа не блокирует последующие эффекты.**
   Для create основной RPC возвращает два корректных созданных booking ID,
   затем `applyPerMinuteBookingTerms` удерживается pending. Сменить пользователя
   и generation, завершить terms с `{ok:true}`: продолжаются selectDate,
   clearDraft, close, refresh, focus и notify в новом контексте.
   Для reschedule удержать `saveBookingColor` после основного ответа, сменить
   сессию и завершить его: продолжаются selectDate, refresh, notify и open(A).

В обоих последних сценариях исходная проверка session уже прошла до следующего
await. Повторной проверки перед дальнейшими операциями и интерфейсом нет.
В reschedule тесте последующая запись заметки намеренно возвращала отказ новой
сессии; даже этот отказ не остановил перенос UI к старому booking ID.

### Как повторить диагностику без запуска всего кабинета

Прочитать `provider.js`, нормализовать CRLF для поиска границ и передать в
`vm.runInContext` неизменённые фрагменты:

- cancel: от `async function cancelBookingSeries(event)` до
  `async function saveBookingBlockNote(event)`;
- reschedule: от `async function saveBookingChanges(event)` до
  `function offlineCandidateSlots(`;
- create: точную ветку `if (occurrenceCount > 1)` непосредственно перед
  `db.rpc('create_minuta_recurring_bookings'` до `const bookingParams =`,
  обернув её в тестовую async-функцию и задав входные переменные.

RPC заменяется управляемым Promise. DOM-идентичность формы A/B и текущие
user/generation изменяются до разрешения Promise; `closeBookingSheet`,
`openBookingSheet`, refresh/notify и отправка уведомления заменяются счётчиками.
Для проверки второго await основной RPC завершается успешно, а обещание цвета
или terms удерживается отдельно. VM должен дождаться входа в эту точку, затем
сменить сессию. Такой harness проверяет контроль потока, а не RLS или игру API.

## Дополнительные ограничения, видимые в коде

- После основного ответа используется только user/generation; переключение
  организации не покрыто этой проверкой. Нужно зафиксировать organization scope,
  не предполагая, что `sessionGeneration` меняется при каждом выборе организации.
- Fulfilled error создания сообщает «Ни одна запись не была добавлена» для
  нераспознанной ошибки; транспортная потеря ответа после commit не доказывает
  отсутствие созданной серии. Аналогично пустой `{data:null,error:null}` сейчас
  может пройти к success с пустым списком created/affected.
- Создание серии и донастройка длительности/цвета не являются одним frontend await.
  Ошибка после основного commit не равна отсутствию серии. Попытка компенсации
  `rollbackCreatedBookings` также имеет собственный результат, который нужно
  учитывать перед утверждением «серия не создана».
- v79 CREATE не принимает request_id для целой серии. Нельзя обещать безопасный
  повтор новой серии после неизвестного результата лишь на основании блокировки
  кнопки или существующей идемпотентности отдельных booking RPC.

## Безопасный план реализации владельцем provider

1. Ввести идентичность открытого booking sheet: incarnation формы, booking ID,
   user/generation и организация. Обновлять её при open/close/back/смене организации
   и reset. Не менять остальной кабинет «заодно».
2. Снимать immutable snapshot входных данных перед записью. Сохранять token
   конкретного запроса, предотвращать двойной submit этой формы; старый finally
   не должен разблокировать новую форму или чужой pending-запрос.
3. Разделить транспортное исключение, доказанный отказ SQL, недостоверный результат
   и подтверждённый commit. Применить catch/finally для восстановления контролов
   только в актуальной форме. Не показывать success по пустому payload.
4. Проверять scope после каждого await и непосредственно перед зависимыми
   запросами/локальным состоянием/уведомлениями/переключением даты/открытием формы.
   Запоздалый callback не отправляет новые сообщения от другой сессии.
5. Для неизвестного CREATE блокировать слепое повторное создание до сверки списка.
   Серверную идемпотентность целой серии проектировать отдельно с владельцем SQL.
   Не добавлять frontend fallback, который после timeout создаёт ту же серию заново.
6. После частично завершённой цепочки показывать точный статус: серия создана,
   дополнительные свойства не подтверждены; либо компенсация подтверждена.
   Не стирать новый черновик и не выдавать попытку компенсации за доказанный rollback.

Нельзя просто оборачивать весь обработчик в общий catch с автоматическим retry:
он может повторить уже подтверждённые сервером действия и побочные уведомления.
Повтор переноса/отмены оценивается по текущему серверному состоянию и отдельному
контракту, без обещания повторной отправки уведомлений ровно один раз.

## Критерии будущей регрессии

- Cancel/create/reschedule: thrown RPC восстанавливает актуальную форму или
  показывает защищённую неопределённость CREATE; нет необработанного rejection.
- Pending A → открыть B → success/error/throw A: B не закрывается, не заменяется
  и не получает ошибку A; её pending token и кнопки не изменяются.
- Повтор submit до ответа даёт один исходный RPC; reset/new session позволяет
  новую независимую форму, старый ответ не снимает её блокировку.
- Переключение org A→B и user/generation до основного ответа или любого следующего
  await не инициирует старые записи, local map updates, сообщения или navigation.
- После reset/logout старые имена, телефоны и заметки не возвращаются в UI/cache.
- Malformed result не сообщает успешное создание/отмену/перенос; изменённый DOM
  после submit не подменяет исходные параметры выполняющейся операции.
- Commit CREATE + потеря ответа не создаёт дубль при пользовательском повторе;
  до серверного nonce-контракта проверяется блокировка и ручная сверка.
- Отказ terms/цвета/заметки после commit и отказ компенсации не показываются как
  полное отсутствие серии. Уже подтверждённые эффекты не повторяются автоматически.
- Существующие v79 static tests остаются; runtime VM tests дополняются настоящим
  browser smoke. Серверные rollback/concurrency/notification гарантии проверяются
  отдельно и не выводятся из заглушек.

Реализация требует согласованного владельца `provider.js`; этот документ
подготавливает ограниченный будущий patch, ничего не устанавливает и не публикует.
