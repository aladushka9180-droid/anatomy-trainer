# Идемпотентное создание группового события

Статус: подготовленный контракт, без реализации SQL, назначения номера миграции
или изменения БД. Срез основы: `9452128916ef1e4b265401578893749782b2e84a`.
Перед реализацией владелец выпуска сверяет свежий `origin/main`, интеграцию CRM
и свободный номер миграции. Этот документ не резервирует номер.

## Причина и существующие гарантии

`supabase-migration-v80.sql`, `upsert_minuta_group_event`, при `p_event = null`
вставляет новое событие и пишет аудит. Потеря ответа после commit и повтор CREATE
могут создать второй черновик: проверка пересечений в
`enforce_minuta_group_event_scope` действует для `published`/`closed`.
Блокировка повторного нажатия в браузере не заменяет серверную идемпотентность.

Текущий защищённый UI при неопределённом результате legacy CREATE сохраняет поля,
обновляет список и блокирует слепой повтор из той же формы. Это остаётся режимом
совместимости до доступности нового RPC. Повтор UPDATE существующего UUID
не создаёт новое событие, но сам по себе не гарантирует единственную запись аудита.

Последний `get_minuta_group_booking_role` находится в v100: он проверяет
авторизацию, активную организацию, активное членство и явно отклоняет NULL role.
Роли: `owner`, `admin`, `specialist`; специалист управляет своим исполнителем.
Эту семантику нельзя заменять более ранней проверкой v80 с неявной обработкой NULL.

## Новые объекты и совместимость API

Предлагаются отдельные RPC без перегрузки или изменения legacy-сигнатуры:

- `get_minuta_group_create_capability(p_organization uuid)` возвращает JSON
  `{ "supported": true, "version": 1 }` после проверки текущего доступа.
- `create_minuta_group_event_once(p_request_id uuid, p_organization uuid,
  p_location uuid, p_performer uuid, p_title text, p_description text,
  p_date date, p_time time, p_duration integer, p_capacity integer,
  p_status text)` возвращает `{ "event_id": "uuid", "status": "draft",
  "idempotent": false }`; повтор возвращает тот же UUID, текущий статус и `true`.

Названия предварительные до реализации и фиксации публичного контракта тестами.
Legacy `upsert_minuta_group_event` продолжает возвращать UUID и не меняется.
Первое создание через новый RPC вызывает его с `p_event = null`.
Публичное бронирование участника `book_minuta_group_event` не меняется.

Новая приватная таблица `group_event_create_requests`:

| Поле | Ограничение и назначение |
| --- | --- |
| `organization_id uuid` | NOT NULL; организация запроса |
| `request_id uuid` | NOT NULL; вместе с организацией образует PRIMARY KEY |
| `actor_id uuid` | NOT NULL; исходный автор, неизменяемый UUID без каскадного удаления/обнуления при удалении учётной записи |
| `normalized_parameters jsonb` | NOT NULL; JSON-объект всех параметров создания после фиксированной нормализации |
| `event_id uuid` | NOT NULL; составной FK `(event_id, organization_id)` на `group_booking_events(id, organization_id)` с ON DELETE RESTRICT |
| `created_at timestamptz` | NOT NULL DEFAULT now() |

RLS включён; прямые права на таблицу отозваны у PUBLIC, anon, authenticated и
service_role. RPC: SECURITY DEFINER, пустой search_path, полностью квалифицированные
имена объектов; execute только authenticated. Владелец функции задаётся проектным
механизмом миграций. Клиент не получает нормализованный payload или чужой UUID.

UPDATE и DELETE ledger запрещаются отдельным триггером с ошибкой
`55000 / group_event_request_immutable`. Нельзя применять каскады или очищать
ключи по сроку: после очистки старый повтор способен создать новое событие.
TRUNCATE и прямые INSERT не разрешены прикладным ролям. Административное удаление
или восстановление таблицы требует отдельного согласованного регламента.

Нормализация фиксирует ВСЕ параметры: организацию, локацию, исполнителя, название,
описание, дату, время, длительность, вместимость и статус. Название и описание
обрезаются по краям как при legacy-сохранении; правила NULL/пустой строки явно
задаются и покрываются тестами. UUID/числа/дата/время сохраняются в каноническом
типизированном представлении. Сравнивается целый JSONB, а не только дата/телефон
или текущие изменяемые поля события. Секреты в payload не входят.

## Транзакция, доступ и повтор

1. Проверить `auth.uid()`, формат nonce и предварительный доступ к организации.
2. Получить transaction advisory lock по `(organization_id, request_id)` с
   отдельным постоянным namespace. Конкретный namespace сверить с репозиторием
   при реализации. Все записи nonce идут только через этот RPC.
3. После возможного ожидания lock заново получить строку организации и членства
   автора с `FOR SHARE`, проверить текущие status/active/role. Использовать
   фиксированный порядок блокировок: организация, затем членство. Блокировки
   держать до конца транзакции. Одной проверки STABLE helper до ожидания недостаточно.
   Если revoke завершился первым, запрос должен отказать; если запрос получил
   блокировку первым, revoke ждёт окончания уже авторизованной транзакции.
4. Прочитать ledger по ключу. Чужой `actor_id` даёт отказ без раскрытия UUID;
   несовпадающий normalized payload даёт mismatch, без INSERT/UPDATE.
5. При существующем совпадающем ключе проверить текущий доступ к связанному событию:
   tenant совпадает; специалист всё ещё является его исполнителем. Вернуть тот же
   UUID и актуальный статус. Не вызывать upsert, не менять событие и не писать
   повторный create audit. Отсутствие цели не разрешает создавать замену.
6. Только если ключа нет — вызвать существующий upsert с `p_event = null` и вставить
   ledger в той же транзакции. Любая ошибка откатывает event, audit и ledger вместе.

Временные проверки `future date`, активность локации и исполнителя выполняются
legacy upsert при первом создании. Их нельзя повторять до lookup успешного nonce:
между commit и повтором событие могло начаться, сменить время или стать отменённым.
Текущая авторизация обязательна и для повтора. Отменённое событие не воскрешается.

Фактическое поведение блокировок при конкурирующем revoke и двух запросах необходимо
подтвердить на PostgreSQL двумя соединениями. Здесь описан требуемый порядок,
а не доказанный результат реализации.

## Ошибки, которые видит клиент

| SQLSTATE / message | Обработка |
| --- | --- |
| `22023 / group_event_request_id_required` | Ошибка до создания; исправить запрос |
| `22023 / group_event_request_mismatch` | Ключ уже существует; не менять nonce и не повторять legacy CREATE |
| `42501 / group_event_request_actor_denied` | Отказ без чужих UUID/данных |
| `P0001 / group_event_request_target_unavailable` | Ledger есть, цель недоступна; не создавать замену |
| `55000 / group_event_request_immutable` | Нарушение внутреннего контракта; не обещать успешную запись |

Унаследованные ошибки авторизации, валидации и конфликтов сохраняют SQLSTATE/message
v100/v80. Доказанный отказ классифицируется точной парой кода и сообщения,
а не подстрокой `full`/`unavailable` в произвольном сетевом исключении.
Mismatch, транспортная ошибка и неполный успешный ответ не доказывают отсутствие
уже созданного события. Ответ должен содержать UUID, допустимый актуальный статус
`draft/published/closed/cancelled` и логический признак повтора.

## Capability и форма

Capability проверяется до CREATE и привязывается к организации/сессии.
Только валидное `supported:false` или точно подтверждённое отсутствие конкретного
capability RPC (`PGRST202`/`42883` с совпадающей идентичностью функции) включает
нынешний protected legacy path. Ошибка сети, авторизации или неполный ответ
блокирует создание до повторной проверки capability.

Для новой поддерживаемой формы создаётся nonce и сохраняется immutable snapshot
отправленных параметров. Пока результат неопределён, поля защищены от изменения,
повтор отправляет тот же nonce и snapshot. Успех или доказанный отказ отображается
по серверному результату. Несовпадение запроса требует сверки, а не генерации нового nonce.
После попытки нового CREATE запрещён автоматический fallback в legacy CREATE —
даже если следующая попытка сообщает отсутствие RPC вследствие отката релиза.

Закрытие формы или переключение организации не разрешает старому ответу изменять
новую форму. Отмена события, подтверждённая ответом replay, отображается как отмена,
а не как вновь созданное активное событие. Определённое пользователем новое создание
после сверки списка получает новый nonce; старый серверный ключ сохраняется.

## Операционный откат

Откат одной транзакцией меняет capability на `supported:false` и отзывает execute
нового CREATE у прикладной роли. Ledger, его триггер, события и аудит сохраняются.
Legacy RPC, v86 overlap trigger и публичные записи участников не изменяются.
Уже начатый new-mode запрос не переключается на legacy после ошибки отката.

Повторное применение миграции восстанавливает capability/GRANT, сохраняя все ключи.
Запрещён старый `recovery/rollback-group-bookings-v80.sql`: он удаляет таблицы
группового модуля. Не требуется и не допускается удалять ledger ради отката UI.
Проверка отката включает заполненный ledger и повтор после повторного применения.

## Приёмка и изоляция следующей реализации

- Одинаковые nonce и payload, в том числе два одновременных соединения: один UUID,
  одно событие, одна запись create audit.
- Изменение каждого поля payload с прежним ключом: mismatch без новых событий,
  изменения исходного события и дополнительного create audit.
- Чужая организация/учётная запись и отозванная роль не раскрывают UUID; изменение
  роли/членства во время ожидания nonce-lock проверяется реальными соединениями.
- Сбой транзакции не поглощает ключ; повтор после commit с потерянным ответом
  возвращает исходный результат. Два конкурентных разных payload не создают два события.
- Изменённое или отменённое после создания событие сохраняет UUID и текущее состояние
  при replay. Недоступная цель не создаётся повторно.
- Legacy-сигнатуры, проверки вместимости/пересечений, tenant FK и порядок trigger v86
  сохранены; повтор не обходит текущие права.
- Capability missing/false, network failure, stale session/org/form и откат между
  capability и CREATE проверены runtime-тестами UI. Неопределённость не запускает fallback.
- Операционный откат с данными, повторное применение и повтор nonce сохраняют
  mapping, события и аудит. Прямые write/delete/truncate прикладных ролей запрещены.

PGlite пригоден для транзакционных, permission и rollback-проверок на фикстуре;
он не доказывает конкуренцию независимых PostgreSQL-соединений. Нужны отдельные
двухсоединительные интеграционные тесты, затем защищённая последовательность выпуска
и реальный UI/RPC E2E. До этого нельзя объявлять серверную идемпотентность внедрённой.

Будущий ограниченный scope: новая миграция, отдельный операционный rollback,
`group-bookings.js`; независимые SQL/runtime-тесты принадлежат QA. Номера миграции,
cache wiring и публикацию назначает единственный владелец выпуска после сверки.
