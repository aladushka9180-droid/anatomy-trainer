# Административная запись участника в закрытую группу

Статус: **план, SQL и интерфейс не реализованы, номер миграции не назначен**.
Документ подготовлен по текущим определениям v80 и исправлению ролевой проверки
v100. Перед реализацией сверяются свежий main, владелец выпуска и действующие
контракты CRM/денежного журнала. Этот файл не запускает миграции.

## Пользовательский результат и граница первого этапа

Администратор принимает запись по телефону и добавляет клиента в закрытое групповое
событие из кабинета, не открывая публичный набор. Он видит подтверждённое сервером
место, участника и историю действия. Повтор после потери ответа не занимает второе
место. Статус посещения не выдаётся за статус оплаты.

Сейчас `group-bookings.js` позволяет сотруднику менять статус уже существующего
участника, но не добавлять нового. `book_minuta_group_event` v80 предназначен для
публичной записи: требует `organization.public_booking_enabled`, включённый модуль,
активную локацию, будущую дату и `event.status = published`; публичный аудит имеет
`actor_id = null`. Отдельной административной операции добавления нет.

В v80 у событий и участников **нет цены, оплаченной суммы, долга или
`client_account_id`**. Участник хранит снимок имени/телефона/комментария и статусы
`confirmed`, `cancelled`, `attended`, `no_show`. Создание участника не может
подразумевать оплату, доход, расход абонемента или нулевой долг.

## Доступ и состояния

Новый отдельный auth-only RPC, предварительное имя
`add_minuta_group_participant(p_organization, p_event, p_request_id,
p_client_name, p_client_phone, p_comment)`, принимает клиента без серверных
секретов. Результат: `participant_id`, `booking_code`, актуальный `status`,
`idempotent`; запрос не принимает произвольного автора аудита.

| Контекст | Правило первого этапа |
| --- | --- |
| Owner/admin активной организации | Добавляет участника к событию этой организации |
| Specialist с активным членством | Добавляет только к событию, где он текущий исполнитель |
| Чужая организация, отозванное членство, anon | Отказ без UUID или данных чужого клиента |
| `published`, будущий сеанс | Административная запись разрешена; публичная запись остаётся прежней |
| `closed`, будущий сеанс | Административная запись разрешена; публичный набор остаётся закрытым |
| `draft` | Отказ: это ещё подготовка, v80 не резервирует время черновика. Для частной группы сначала явно сохранить состояние `closed` |
| `cancelled` или уже начавшийся сеанс | Новое участие запрещено; исторический ввод остаётся отдельным будущим сценарием |
| Модуль групп выключен, организация/локация неактивны | Новое участие запрещено; история сохраняется |

`active` — состояние организации/членства/локации, а не допустимый статус события.
Флаг публичной записи организации не ограничивает административную запись:
частный набор должен работать при `public_booking_enabled = false`.
Отключение модуля групп в целом, напротив, запрещает новые действия.

Проверка использует семантику `get_minuta_group_booking_role` из v100, включая
явный отказ для NULL role. Текущий доступ проверяется повторно после ожидания
блокировки: организация и членство автора блокируются `FOR SHARE` до конца
транзакции. Перед replay проверяется текущий исполнитель события для специалиста.
Отозванная роль не получает результат прежнего запроса.

## Транзакция, вместимость и идентификатор запроса

Не вызывать публичный `book_minuta_group_event`: он намеренно отказывает для closed.
Новый RPC вставляет участника непосредственно в рамках защищённой серверной
операции, используя существующие таблицы, tenant FK и ограничения v80.

Нужен приватный неизменяемый журнал административных запросов, связывающий
nonce, организацию, автора, полный нормализованный payload и UUID участника.
Записи UPDATE/DELETE запрещены, прямых прикладных прав нет, RLS включён,
FK `(participant_id, organization_id)` сохраняет принадлежность организации.
Удаление участника не должно каскадно стирать ключ запроса.

Порядок:

1. Проверка авторизации и формата запроса; общий с публичным бронированием
   advisory lock по `request_id` с существующим namespace `8003`.
2. Повторная проверка актуального доступа после ожидания; lookup административного
   журнала. Совпавшие nonce/автор/полный payload возвращают исходный UUID и текущий
   статус без нового INSERT или аудита. Иной payload — mismatch без изменения данных.
3. Если nonce уже существует в публичных участниках или относится к другой
   организации/автору, отказ без раскрытия чужого результата. У v80
   `group_booking_participants.request_id` глобально уникален: это нельзя
   заменить несовместимым предположением об уникальности только внутри организации.
4. Для первого добавления получить общий event advisory lock `8002`, затем
   event row `FOR UPDATE`. Проверить статус, время в timezone локации, настройки,
   активную локацию/исполнителя и доступ к событию.
5. Проверить дубликат телефона и число участников со `status <> cancelled`.
   `confirmed`, `attended` и `no_show` занимают место по текущей семантике v80.
   Нельзя вводить обход вместимости для администратора.
6. Одной транзакцией создать участника, запись nonce-журнала и аудит с текущим
   `auth.uid()`. При ошибке ни один объект не сохраняется.

Сохранить частичный уникальный индекс `(event_id, phone_digits)` для неотменённых
участников. На первом этапе использовать действующую нормализацию v80; переход
к российской нормализации `8 → 7` требует отдельного анализа уже существующих
дубликатов, а не скрытой смены правила.

Отмена не удаляет строку. Новое явно подтверждённое зачисление после отмены — новый
nonce и новая строка, история предыдущего участия остаётся. Повтор старого nonce
возвращает `cancelled`, не восстанавливает место. Восстановление старой строки
существующим status RPC и новая запись конкурируют за то же последнее место.

Порядок блокировок нужно проверить против текущего
`set_minuta_group_participant_status`: он сначала блокирует participant row,
затем event advisory lock. Новый путь не должен блокировать старую строку
участника после event lock с целью её восстановления. Конкуренция изменения
вместимости и зачисления также требует отдельного двухсоединительного теста.

## Публичный путь и защита истории

Публичная выдача событий не должна раскрывать closed/draft и данные участников.
Если закрытую группу позже публикуют, ранее занятые административно места входят
в общее число занятых мест; имена и телефоны не входят в публичный каталог.

Есть обязательная точка совместимости: нынешний public RPC v80 выполняет replay
`request_id` до проверки `event.status`. Новый административный источник должен
быть отличим по приватному журналу. При совпадении request_id с административным
участником публичная replay-ветка обязана отказать без выдачи UUID/кода/статуса,
даже если переданы известные event и телефон. Одной недоступности closed в каталоге
недостаточно. Публичные запросы, созданные прежним публичным RPC, сохраняют
прежнюю идемпотентность. Это узкое изменение проверки replay, не разрешение
анонимному пользователю записываться в закрытую группу.

Административный аудит: отдельное действие `group_participant_admin_added`,
organization/event/participant, фактический actor, источник `staff`, количество
занятых мест после операции. Полные имя/телефон/комментарий не дублируются в details.
Их снимок остаётся в защищённой строке участника. Повтор nonce не пишет второй
аудит. Отмена и посещение остаются отдельными историческими действиями.

## Клиентская карточка и деньги

Историю участия можно показывать в карточке только через защищённый поиск внутри
доступной организации по нормализованному телефону, сохраняя различие источников
«индивидуальный визит» и «участие в группе». Нельзя создавать фиктивную строку
`bookings` ради попадания в существующую историю: это повторно резервирует время
и может исказить аналитику, уведомления и платежи.

Существующий `client_accounts` v54 — глобальная учётная запись с access-code hash,
а не простой контакт CRM. Административное добавление телефона не создаёт пароль,
сессию или публичный доступ к истории. Если следующий этап добавит
`client_account_id`, он связывается только с уже существующей проверенной
идентичностью и tenant-доступом, без автоматического объединения по чужому телефону.
Групповое участие само по себе не обходит booking-based проверки абонементов v73.

Первый этап не создаёт денежных проводок и не показывает «оплачено»/«долг 0».
Платная группа требует отдельного ценового снимка на участника, начисления
обязательства и привязки успешных денежных операций из
`MONEY_LEDGER_CONTRACT.md`. Только тогда долг считается по начислению и
распределённым оплатам/возвратам. Посещение, отмена, погашение абонемента,
получение денег и банковский возврат — разные события. Отмена участия не означает
денежный возврат и не стирает денежную историю.

## Неопределённость, отключение и откат

UI фиксирует nonce и полный payload на попытку. Потеря ответа позволяет только
повтор неизменного запроса; не создаётся новый nonce и не вызывается публичный RPC.
Точная пара SQLSTATE/message отличает доказанный отказ до создания от mismatch
или неизвестного результата. При отказе по вместимости можно исправить/выбрать
другое событие; при неопределённости сначала сверяется исходная попытка.
Ответ cancelled отображает отмену, без ложного подтверждения нового места.

Операционный откат отключает новое добавление/отзывает новый RPC, сохраняя
участников, nonce-журнал, provenance и аудит. Публичная защита replay для
административного источника сохраняется и после отката. Нельзя удалить эту защиту
раньше закрытия доступа ко всем уже созданным административным участникам.
Повторное включение использует прежние ключи; старый destructive rollback v80
не применяется. UI capability проверяется до записи; отсутствие функции не
переключает административное добавление на публичный endpoint.

## Восемь критериев приёмки

1. **Роли и tenant.** Owner/admin добавляют в свою организацию, specialist —
   только к своему событию; чужой tenant и revoke во время ожидания дают отказ
   без чужих UUID/PII. Повтор nonce также перепроверяет доступ.
2. **Состояния.** При закрытой публичной записи staff добавляет в future closed;
   anon не может. Draft/cancelled/начавшийся сеанс и выключенный групповой модуль
   отказывают; публикация closed не теряет ранее занятые места.
3. **Последнее место.** Два соединения, staff/public, staff/restore и staff/capacity
   change: нет превышения capacity, дублей и необъяснённого частичного результата.
   Deadlock/rollback не потребляет nonce; повтор сохраняет корректную вместимость.
4. **Nonce и payload.** Одинаковый запрос создаёт одного участника и один аудит;
   изменение каждого поля, другой actor/org и коллизия с public request не раскрывают
   старый результат и не создают новую строку. Потеря ответа после commit безопасна.
5. **Публичная граница.** Передача в public RPC nonce административной записи,
   event и телефона не раскрывает private UUID/код/статус; обычный public replay
   продолжает работать. Public каталог не выдаёт PII закрытой группы.
6. **История.** Отмена сохраняет исходную строку; старый replay показывает cancelled.
   Явное новое зачисление имеет новый nonce, код и audit, не переписывает посещение.
7. **CRM и деньги.** Участие видно только в разрешённой истории организации,
   не создаёт фиктивный booking/клиентский вход, оплату, доход или долг 0;
   отдельные денежные операции и подтверждённая идентичность проверяются отдельно.
8. **Откат с данными.** Отключение и повторное включение не теряют участников,
   nonce, provenance и аудит; private public-replay guard остаётся; повтор после
   отката не создаёт дубль. UI не делает fallback после неопределённого ответа.

До реализации нужны SQL/rollback/runtime-тесты, реальная конкуренция независимых
PostgreSQL-соединений и затем проверка UI. Документ и тестовая фикстура сами по
себе не доказывают работу сценария в production.
