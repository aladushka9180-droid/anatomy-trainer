# Аварийное восстановление Minuta

## Ответственность и целевые сроки

- Ответственный за объявление аварии, выбор точки восстановления и возврат сервиса пользователям: владелец репозитория `anatomy-trainer` и рабочего проекта Supabase Minuta.
- Исполнитель восстановления: технический администратор с доступом к GitHub Actions, внешнему backup-bucket, паролю шифрования и Supabase.
- Резервный исполнитель: назначенный владельцем администратор с отдельной учётной записью и доступом к сохранённой офлайн-копии этой инструкции.
- RPO: не более 24 часов при ежедневных успешных копиях.
- RTO: до 4 часов для восстановления записи и кабинета; до 8 часов для возвращения файлов Supabase Storage, если они затронуты.

Если ответственный недоступен, исполнитель может восстановить данные только в новом изолированном проекте. Переключать рабочий сайт на восстановленный проект без решения ответственного нельзя.

## Когда начинать восстановление

Восстановление требуется при подтверждённой потере или повреждении данных, невозможности штатного отката миграции либо недоступности текущего проекта Supabase дольше допустимого RTO. Сбой GitHub Pages или одного RPC сначала устраняется возвратом фронтенда и не является основанием перезаписывать базу.

## Первые действия

1. Зафиксировать UTC-время обнаружения, симптомы, последний известный корректный момент и инициатора решения.
2. Остановить публикации и миграции. Не удалять текущий проект и не запускать `pg_restore --clean` против него.
3. Сохранить журналы Supabase и GitHub Actions, текущий commit сайта и результаты production health.
4. В S3 проверить свежие записи `journal/YYYY/MM/*.json`. Выбрать последнюю копию, завершённую до повреждения, и сверить её `objectKey`, SHA-256 и `retentionUntilUtc`.
5. Если журналов за последние 24 часа нет, считать RPO нарушенным и немедленно уведомить ответственного.

## Восстановление базы

1. Создать новый изолированный проект Supabase или использовать выделенный пустой recovery-проект. Его project ref не должен совпадать с production.
2. Скачать выбранные `.dump.gpg` и `.sha256` из внешнего bucket на защищённую рабочую машину.
3. Сверить хеш до расшифровки:

   ```bash
   test "$(sha256sum minuta.dump.gpg | awk '{print $1}')" = "$(tr -d '[:space:]' < minuta.dump.gpg.sha256)"
   ```

4. Расшифровать и проверить структуру архива:

   ```bash
   printf '%s' "$BACKUP_ENCRYPTION_PASSWORD" | gpg --batch --yes --pinentry-mode loopback --passphrase-fd 0 --output minuta.dump --decrypt minuta.dump.gpg
   pg_restore --list minuta.dump >/dev/null
   ```

5. Ещё раз проверить, что переменная указывает на новый проект, после чего восстановить:

   ```bash
   pg_restore --exit-on-error --clean --if-exists --no-owner --no-privileges --dbname="$MINUTA_RECOVERY_DB_URL" minuta.dump
   ```

6. Сразу удалить незашифрованный `minuta.dump` безопасным способом, принятым на рабочей машине.

## Проверка до переключения

Проверить в восстановленном проекте:

- наличие и количество `services`, `bookings`, `booking_events` и актуальных миграционных таблиц;
- получение свободных окон и открытие записи по коду управления;
- вход исполнителя, перенос и отмену отдельной тестовой записи;
- отсутствие ошибок RLS, RPC и ограничений пересечения интервалов;
- соответствие времени последней записи выбранному RPO.

Далее опубликовать фронтенд с новым URL и anon key только после решения ответственного, запустить production health и наблюдать ошибки минимум 60 минут. Старый проект оставить неизменным для расследования, пока ответственный не закроет инцидент.

## Supabase Storage

Дамп PostgreSQL содержит строки `storage.objects`, но не двоичные фотографии. Если повреждён bucket `portfolio-images`, восстановить объекты из отдельной копии Storage, затем выборочно сверить пути со строками `portfolio_photos`. Если отдельной копии нет, не создавать пустые файлы по метаданным: зафиксировать потерю и скрыть недоступные фотографии из публичного интерфейса после решения ответственного.

## Закрытие аварии

Записать фактические RPO/RTO, точку восстановления, выбранный журнал, SHA-256 архива, новый project ref, результаты проверки и список потерянных данных. После устранения причины выполнить новый backup и отдельный restore drill. Секреты, пароли и полные строки подключения в отчёт не включать.
