# Дополнительные услуги: Pro и серверный кандидат

Цель: мастер связывает основные услуги с дополнением у себя, задаёт пользу, скидку (нет / проценты / целые рубли), реальные дополнительные минуты и видимость. Предпросмотр показывает цену дополнения и всего визита. Клиентские четыре критерия пока приняты на сайте 0 из 4.

Кандидат: независимый модуль Pro, загрузка формы по требованию без блокировки стартового экрана; две additive миграции с owner/RLS-проверками, ревизиями, расчётом условий, одним атомарным визитом, текущим составом услуг и резервированием ресурсов. Исходная квитанция запроса неизменна. Выключение публичных RPC сохраняет уже созданные визиты и их resource lifecycle; disable-файл не удаляет таблицы или данные.

Локально проверены контракт, шесть состояний тем/ширин 390/760/1440, сохранение/повторная загрузка/отключение на fake RPC, отказ backend, права, ревизии, смена сессии и повторный клик. Отдельно проверены lazy loader, существующий сервисный контракт, JavaScript syntax и PWA URL/version contract. Стартовый shell вырос ровно на 1419 измеренных байт относительно v1080; форма и её assets остаются optional, бюджет повышен только до точного итогового размера без запаса. Это измерение размера, не live-доказательство скорости.

SQL: синтетический disposable fixture использует канонические v53 initializer и v69 allocator/requirements; 39/39 последовательных PGlite checks прошли. Подготовлены три настоящих конкурентных сценария PostgreSQL17. PGlite и отдельный PostgreSQL17 CI не являются full-schema restore или production proof. Нативные конкурентные сценарии и статус CI проверять на финальном SHA; полная копия схемы, Auth, RLS, privileges, внешние зависимости и данные должны пройти действующий restore gate владельца перед выпуском.

Владелец Pro/production SQL: существующая задача «КААРДИНАТОР». Доставка владельцу и принятие в очередь пока не подтверждены. Только владелец: свежий main → сверка source hashes и migrations → свежий подтверждённый backup → privilege-preserving isolated restore → обе migrations и scoped tests → disable/reapply/preservation → разрешённый SQL deploy → Pro и клиентский пакет → live-приёмка. На интеграции назначить свежую общую версию PWA и повторить redirect/precache checks. Production SQL здесь не применялся.

Клиентская зависимость: `aladushka9180-droid/primetime-client`, ветка `codex/client-addon-offers-20261007`. До общего выпуска обычная запись должна продолжать работать при недоступном новом API.

Открыто: правило поминутных услуг ждёт ответа; кандидат допускает только фиксированные услуги. Live baseline/after не получены: Computer Use остановлен политикой из-за неопределённого URL Chrome; обход не выполнялся. Производственные визиты и настройки для тестов не создавались/менялись.
