# Дополнительные услуги: Pro и серверный кандидат

Цель: мастер связывает основные услуги с дополнением у себя, задаёт пользу, скидку (нет / проценты / целые рубли), реальные дополнительные минуты и видимость. Pro показывает предпросмотр предложения; клиент — итог всего визита. Четыре критерия пока приняты на сайте 0 из 4.

Кандидат: независимый модуль Pro, загрузка формы по требованию без блокировки стартового экрана; три additive миграции с owner/RLS-проверками, ревизиями, расчётом условий, одним атомарным визитом, текущим составом услуг и резервированием ресурсов. Исходная квитанция запроса неизменна. Выключение публичных RPC сохраняет уже созданные визиты и их resource lifecycle; disable-файл не удаляет таблицы или данные.

Согласованное продолжение: для поминутной допуслуги мастер обязательно задаёт `addon_price_rub` — целые рубли за всё дополнение до скидки, 0..1000000, и отдельно фактические дополнительные минуты, 0..480. Нулевая цена допустима только явно; пустая цена отклоняется. Обычная фиксированная допуслуга использует каталог, отдельную цену задать нельзя. Основная услуга остаётся фиксированной; тариф и режим обычной поминутной услуги не меняются. При смене режима в каталоге старое предложение скрывается до пересохранения мастером.

Локально проверены контракт, шесть состояний тем/ширин 390/760/1440, сохранение/повторная загрузка/отключение на fake RPC, отказ backend, права, ревизии, смена сессии и повторный клик. Отдельно проверены lazy loader, существующий сервисный контракт, JavaScript syntax и PWA URL/version contract. Стартовый shell вырос ровно на 1419 измеренных байт относительно v1080; форма и её assets остаются optional, бюджет повышен только до точного итогового размера без запаса. Это измерение размера, не live-доказательство скорости.

SQL: синтетический disposable fixture использует канонические v53 initializer и v69 allocator/requirements; 55/55 последовательных PGlite checks прошли, включая отдельную цену, нулевое время, ресурсы, неизменную квитанцию, устаревшую ревизию, архивирование и source/ACL drift. Прежний CI на 6d2fb81a полностью зелёный, но не доказывает новое продолжение с поминутным дополнением: нужен CI точного обновлённого HEAD, включая native PostgreSQL17 и три конкурентных сценария. Ни fixture, ни CI не являются full-schema restore или production proof: полная копия схемы, Auth, RLS, privileges, внешние зависимости и данные должны пройти действующий restore gate владельца перед выпуском.

Владелец Pro/production SQL: существующая задача «КААРДИНАТОР». После прямого разрешения человека сообщения обоим владельцам доставлены; клиентский пакет сохранён в долговечной очереди HOLD, принятие Pro пока не подтверждено. Только владелец: свежий main → сверка source hashes и migrations → свежий подтверждённый backup → privilege-preserving isolated restore → все три migrations и scoped tests → disable/reapply/preservation → отдельно разрешённый SQL deploy → Pro и клиентский пакет → live-приёмка. На интеграции назначить свежую общую версию PWA и повторить redirect/precache checks; optional offer assets теперь v2. Production SQL здесь не применялся.

Клиентская зависимость: `aladushka9180-droid/primetime-client`, ветка `codex/client-addon-offers-20261007`. До общего выпуска обычная запись должна продолжать работать при недоступном новом API.

Открыто: CI обновлённого HEAD, подтверждение очереди Pro, full restore/rollback и согласованный выпуск. Live baseline/after не получены: Computer Use остановлен политикой из-за неопределённого URL Chrome; обход не выполнялся. Производственные визиты и настройки для тестов не создавались/менялись.
