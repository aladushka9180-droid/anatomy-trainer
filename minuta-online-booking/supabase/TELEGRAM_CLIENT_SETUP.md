# Уведомления клиентам в Telegram

После записи клиент нажимает «Получать уведомления в Telegram» и подтверждает доступ. Подключение сохраняется активным только после успешной проверки, что бот может написать этому Telegram ID. Затем события обрабатывает единый outbox; браузер не отправляет дублирующее сообщение.

Типы событий и каналы включаются в едином центре уведомлений организации. Само наличие Telegram ID не включает рассылку.

## Переменные функции

Используется уже сохранённый в Supabase `TELEGRAM_BOT_TOKEN`. `SUPABASE_URL` и `SUPABASE_SERVICE_ROLE_KEY` автоматически доступны Edge Function в проекте Supabase.

Для планировщика нужен `NOTIFICATION_DISPATCHER_SECRET`; он передаётся только в `x-worker-secret`. Секреты не добавляются в браузер, GitHub или исходный код.

## Активация

1. Применить исходные Telegram-миграции, v77, v88 и затем `supabase-migration-v114.sql`.
2. В BotFather выполнить `/setdomain` для клиентского бота и указать `aladushka9180-droid.github.io`. Без привязанного домена Telegram Login отклонит авторизацию.
3. Развернуть `notification-dispatcher` и `telegram-client-notify`. `/authorize` проверяет HMAC-подпись Telegram, токен записи и фактический доступ бота к чату.
4. Старый маршрут `/connect` оставлен только для ранее закэшированных страниц. Он продолжает устанавливать webhook на адрес
   `https://cawexmmrqjvothcbgjxr.supabase.co/functions/v1/telegram-client-notify`
   с секретной проверкой запросов.
5. Применить v114 без включения организаций, развернуть обе Edge Function и создать
   одну активную задачу `minuta-notification-dispatcher` раз в минуту по инструкции
   в `supabase/functions/notification-dispatcher/README.md`.
6. Вызвать защищённый `/cutover-ready` переходной Telegram-функции, затем в течение
   15 минут по одной организации явно включать client/telegram и общий переключатель
   и выполнять защищённый dry-run activation. До успешной активации продолжает работать
   legacy Telegram; после неё организация обслуживается только unified worker.
   Последняя активация удаляет `telegram-client-reminders-hourly`, предварительно
   подтвердив активный replacement.
7. Опубликовать клиентские файлы одной актуальной версии кэша.

Для безопасного отката использовать `supabase-migration-v114-rollback.sql`. Он
сохраняет очередь, endpoints и routing-state и не переключает cron. Он проверяет, что
для каждой уже активированной организации остаётся replacement, а для ещё не
активированных — legacy cron.

## Проверка

1. Создать тестовую запись на новый номер.
2. На странице успеха нажать «Получать уведомления в Telegram» и разрешить отправку сообщений в окне Telegram.
3. Убедиться, что страница показывает «Telegram подключён», а ожидающее событие имеет статус «в очереди».
4. Запустить диспетчер с подменённым Telegram-ответом и проверить статус «отправлено». Для Telegram не показывать «доставлено».
5. Перенести запись — должно прийти обновление.
6. Отменить запись — должно прийти уведомление об отмене.
7. Напоминание проверять только в изолированной базе и с подменённым шлюзом: старые напоминания после переноса/отмены должны перейти в `cancelled`.
8. Смоделировать timeout после отправки: событие должно перейти в
   `telegram_delivery_unknown`, не возвращаться в pending после истечения lease и
   не разрешать обычный retry. Это не доказательство доставки — требуется ручная
   сверка до любого повторного сообщения.

Секреты нельзя добавлять в `config.js`, Git или код сайта.
