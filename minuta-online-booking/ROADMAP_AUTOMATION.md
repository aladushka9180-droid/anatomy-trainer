# Автоматизация плана PrimeTime Pro

Этот документ задаёт нормативные правила выбора следующей задачи из
`PRIMETIME_PRO_ROADMAP.md`. Он не разрешает обходить подтверждения, защитные
проверки production или требования к единственному владельцу выпуска.

Активный координатор — heartbeat `PrimeTime Pro — следующий этап`, ID
`primetime-pro`, интервал 3 минуты. Он прикреплён к основной задаче PrimeTime Pro,
молчит при неизменном состоянии и подключает до трёх агентов только для конкретных
непересекающихся участков. Heartbeat не является доказательством готовности:
источником решения остаются `roadmap/plan.json`, `roadmap/status.json` и результаты
read-only gate workflow.

## Формат состояния

Координатор и автоматизация используют следующие машиночитаемые значения:

| Статус | Значение |
| --- | --- |
| `not_started` | Работа и проверяемые доказательства ещё не начаты |
| `implementing` | Идёт анализ, реализация или безопасная локальная проверка |
| `awaiting_external` | Продолжение требует внешнего аккаунта, секрета, провайдера или физического устройства |
| `awaiting_human` | Следующее действие требует решения, проверки или подтверждения человека |
| `verifying` | Реализация опубликована, но не собраны все обязательные доказательства |
| `done` | Все обязательные критерии закрыты допустимыми и актуальными доказательствами |
| `failed` | Обязательная проверка не прошла; следующий этап не запускается |

Состояние одного пункта должно быть представимо такой записью YAML. Это эталон
полей, а не место для секретов или персональных данных:

```yaml
schema_version: 1
roadmap_commit: 40-символьный-SHA-коммита-плана
evaluated_main_sha: 40-символьный-SHA-проверенного-main
item:
  id: D01
  stage: 0
  status: awaiting_external
  dependencies: []
  parallel_group: stage0_safe_preparation
  production_sha: null
  ui_version: null
  gates:
    - id: payment_test_full_refund
      required: true
      result: pending
      execution: manual_gate
      evidence: null
  blockers:
    - id: yookassa_test_credentials
      type: secret
      owner: product_owner
      resolved: false
  next_allowed:
    action: collect_secret_in_provider_console
    execution: human
    reason: Secret must not be requested or stored in chat or repository
```

`blockers[].type` принимает только `secret`, `account`, `provider`, `device`,
`human_decision`, `human_confirmation`, `production_access` или `legal`.
`gates[].execution` принимает `automatic`, `automatic_after_prerequisites` или
`manual_gate`. `result` принимает `pending`, `pass`, `fail` или `expired`.

## Доказательства

Каждое доказательство содержит минимум:

```yaml
kind: workflow_run
url: https://github.com/owner/repository/actions/runs/123
run_id: "123"
head_sha: 40-символьный-SHA
environment: production-like
checked_at: 2026-09-08T12:00:00Z
expires_at: 2026-10-08T12:00:00Z
artifact_sha256: null
scope: payment_full_refund
result: pass
```

Допустимые `kind`: `workflow_run`, `deployment`, `provider_receipt`,
`payment_receipt`, `restore_journal`, `device_report`, `manual_acceptance` и
`production_observation`. В репозиторий и журналы нельзя помещать секреты, ПДн,
полные платёжные реквизиты, содержимое уведомлений или восстанавливаемые файлы.
Внешние идентификаторы маскируются, но должны позволять владельцу проверить
операцию в кабинете поставщика.

Доказательство считается актуальным, если оно относится к текущему `main` либо
после его `head_sha` не менялись файлы его `scope`. Для живых платежей и доставки
срок актуальности равен 30 дням, для backup — 26 часам, для учебного restore —
35 дням, для тревоги — 90 дням. Проверка физического устройства действует для
текущей major-версии PWA, пока не менялись установка, service worker, Auth,
Push, камера, загрузка файлов или офлайн-контур.

## Правила перехода

Пункт получает `done`, только если одновременно:

1. все обязательные `gates` имеют `result: pass`;
2. доказательства относятся к требуемой среде и не истекли;
3. выполнены все зависимости;
4. опубликованный SHA присутствует в `main`, CI и production;
5. обязательное ручное решение имеет ссылку на `manual_acceptance` без секретов;
6. не осталось неразрешённых блокеров.

Следующий пункт автоматически запускается только при свободном release-owner и
`execution: automatic` или `automatic_after_prerequisites`. Автоматизация может
выполнять анализ, создавать отдельный worktree/ветку, подключать агентов для
непересекающихся областей, реализовывать код и запускать безопасные проверки.

Она обязана остановиться непосредственно перед:

- вводом или изменением секретов;
- реальным платежом, выплатой, чаевыми или возвратом;
- массовой или адресной отправкой реальному клиенту без заранее утверждённого
  тестового получателя;
- восстановлением с записью в production;
- удалением облачных данных;
- действием в чужом сайте, карточке организации, DNS или OAuth-кабинете;
- проверкой, требующей физического Android/iPhone или системного разрешения;
- решением о SLO, финансовой модели, признаках прогноза или критерии полезности.

Если первый пункт этапа остановлен внешним блокером, автоматизация не помечает
его пропущенным. В этапе 0 разрешена безопасная параллельная подготовка D02, D03
и D05; D04 ожидает устройства. Этап 1 не открывается, пока D01–D05 не `done`.

Если отдельное действие требует подтверждения, доступа, секрета или ручного шага
пользователя, автоматизация не выполняет и не имитирует его. Она сохраняет точный
блокер, продолжает независимую безопасную работу и не повторяет один и тот же
запрос при каждом запуске. После исчерпания доступной безопасной работы она одним
сообщением перечисляет отложенные действия и спрашивает: «Для этих действий
требуется ваше подтверждение. Подтверждаем?». Без подтверждения зависимый пункт и
этап не считаются завершёнными.

После этапа 0 параллельно разрешены D06 и D09 отдельными владельцами файлов и
миграций. D07 зависит от D06; D08 и D14 — от D01 и D06. Ветвь привлечения идёт
D10 → D11 → D12 → D13. Этап 2 открывается только после закрытия D06–D14 и идёт
D15 → D16 → D17 → D18 → D19 → D20 → D21 → D22.

## Критерии закрытия этапов

```yaml
stages:
  - id: 0
    status: implementing
    required_items: [D01, D02, D03, D04, D05]
    completion: all_items_done
    required_evidence:
      - live_payment_and_full_and_partial_refund
      - real_delivery_minimum_channel_set
      - isolated_auth_and_storage_restore
      - android_and_iphone_device_reports
      - slo_dashboard_and_alert_drill
    opens_stage: 1
  - id: 1
    status: not_started
    required_items: [D06, D07, D08, D09, D10, D11, D12, D13, D14]
    completion: all_items_done
    required_evidence:
      - desktop_and_mobile_scenarios
      - role_matrix
      - tenant_isolation
      - money_journal_reconciliation
    opens_stage: 2
  - id: 2
    status: not_started
    required_items: [D15, D16, D17, D18, D19, D20, D21, D22]
    completion: all_items_done
    required_evidence:
      - safety_gates
      - numeric_kpi_results
      - real_pilot_or_user_study
    opens_stage: null
```

`opens_stage` срабатывает только после повторной проверки доказательств на свежем
`main`. Наличие незавершённого необязательного эксперимента не блокирует этап, но
каждый пункт из `required_items` обязателен и не может быть заменён общим баллом.

## Следующий разрешённый пункт

При текущем состоянии плана D01 остаётся первым незавершённым пунктом, но его
внешние стоп-гейты не разрешают автономный платёж. Поэтому автоматизация должна:

1. продолжить D01 только до безопасной границы подготовки;
2. при достижении границы записать `awaiting_external`, точный блокер и одно
   требуемое действие человека;
3. автоматически передать свободным агентам непересекающуюся подготовку D02,
   D03 и D05;
4. не открывать этап 1 до фактического `done` всех D01–D05.
