Статус 27.09.2026: **локальный кандидат**, production SQL и UI не выпущены.
Владелец изменений и будущего выпуска — эта офлайн-задача; полоса выпуска
PrimeTime Pro сверяется с владельцем UI-аудита непосредственно перед каждым
внешним шагом. Точный SHA кандидата на момент подготовки: `58c9a535`; после
изменения кода, `main` или номера миграции SHA и хеши фиксируются заново.

  v82. Браузерный кандидат прошёл локальное сохранение, перезагрузку, конфликт,
  390/760/1440 и выдачу PWA-ресурсов без сети. Это **не** проверка на полном

- Исходные четыре SQL-файла в `58c9a535` имеют SHA-256:

  - `supabase-migration-v182.sql`: `0be211a5ee6dd50cc8638e759bfda1bf410155f7f172d40b5686239cee3b79f8`;

## Точный подготовительный порядок

1. На новом актуальном `main` проверить уникальность v181/v182, владельца
   выпуска, состав кандидата и неизменность четырёх SQL-хешей. Выделить
   просмотренный SQL-only SHA, содержащий только v181/v182 и оба rollback;
   UI-ветку не использовать как источник исполняемого SQL для protected job.
2. По отдельному точному разрешению выполнить один ручной
   `Minuta Supabase encrypted backup` на SHA текущего `main` с
   `destination=github-artifact-only`. Источник — только production PostgreSQL
   через секрет `SUPABASE_DB_URL` защищённого окружения `minuta-production`.
   Результат — custom `pg_dump`, AES-256 `.dump.gpg`, SHA-256 и журнал в GitHub
   artifact на 35 дней; S3/Telegram отключены этим выбором. Проверить
   `pg_restore --list`, расшифровку с побайтовым сравнением и срок хранения.
   Пароль не запрашивать и не выводить. Текущий backup workflow вызывает
   `notify-health-failure.mjs` при ошибке; перед разрешённым запуском нужно
   либо узко отключить это уведомление для данной репетиции, либо получить
   отдельное разрешение на реальное сообщение. При любом сбое остановиться.
3. Защищённый `minuta-supabase-restore-drill.yml` сейчас принимает для
   кандидата только v180. До запуска отдельно просмотреть и разрешить узкое
   расширение **только** для пары v181/v182 с фиксированным SQL-only SHA,
   хешами, свежим backup run ID и SHA основы. Без такого расширения не
   запускать `candidate_version=none` как замену проверке миграций.
4. Одним разрешённым ephemeral run восстановить backup на runner в PostgreSQL
   17 Docker с `--network none`. Цель — одноразовый контейнер, **не**
   production и **не** постоянная testDB. Использовать штатную фильтрацию
   outbound webhooks, восстановить весь `public` schema/data и инертные Auth
   UUID-заглушки. Managed Auth/Storage, файлы Storage и внешние сообщения
   не восстанавливаются: такой результат доказывает совместимость полной
   продуктовой `public`-схемы, но не полную managed-схему Supabase.
5. До тестовых записей измерить агрегатные counts/fingerprints `services`,
   `inventory_items`, `bookings`, складского аудита и зависимых функций.
   Применить v181, затем v182; проверить RPC signatures, grants, RLS, ledger
   и неизменность существующих строк. Пока ledgers пусты, выполнить rollback
   в обратном порядке (v182 → v181), доказать отсутствие новых RPC/ledger и
   неизменность строк, затем повторно применить v181 → v182.
6. Только на созданных в контейнере синтетических организации, акторе,
   услуге и позиции двумя соединениями проверить конфликт версии, тот же
   request ID, потерянный ответ с повтором, чужую организацию и удаление
   после сохранения. Проверить, что успешный повтор не создаёт вторую строку
   и аудит; старый снимок не перезаписывает новые поля. После заполнения
   ledgers **не** запускать schema rollback: оба rollback SQL справедливо
   запрещают удаление журнала принятых запросов.
7. В артефакт проверки записать только SHA, версии PostgreSQL, агрегатные
   counts и булевы результаты apply/rollback/reapply/integration. Не выводить
   персональные строки, plaintext dump или приватный лог. Удалить контейнер,
   расшифрованный архив и временные файлы даже при ошибке. Любой сбой — стоп.

## После репетиции: отдельное решение о production

Успех isolated run сам по себе не разрешает production SQL. Нужны новое
точное разрешение на однократное применение v181 и v182, свежий backup и
read-only preflight в момент выпуска. Применять последовательно одним
владельцем, проверить функции/права, пустые ledgers и отсутствие изменения
`services`, `inventory_items`, `bookings` и остатков до выпуска UI. Затем
интегрировать UI/PWA с актуальным номером кэша обычным push в `main`, дождаться
целевых CI/Pages и проверить реальные байты, экран и безопасное действие без
создания рабочих записей. Физическая Android PWA проверяется отдельно.

## Откат и восстановление

- Если v182 не применится после v181 до приёма запросов, откатить v181 его
  rollback SQL; оба файла транзакционные. Если UI уже опубликован, сначала
  вернуть прежний интерфейс новой версией SW-кэша и оставить локальные
  черновики как неподтверждённые, без автоматической повторной отправки.
- При пустых ledgers схема откатывается **v182 → v181**. При непустом ledger
  schema rollback запрещён: сохранить RPC и журналы повтора, отключить путь
  отправки через UI и разбирать конкретные записи отдельно. Откат UI не
  удаляет уже подтверждённые изменения каталога.
- Полное восстановление production из dump могло бы потерять все записи и
  платежные/складские изменения после времени снимка. Оно не входит ни в
  разрешение на backup/репетицию, ни в разрешение на миграцию; для него нужны
  отдельный план сверки новых данных и точное разрешение. Цель restore в
  данном плане — только одноразовый контейнер без сети.

## Текущий внешний блокер

Существующий protected ephemeral workflow и `ephemeral-restore-drill.sh`
допускают только v180. Для v181/v182 нет разрешённого запуска полной копии
продуктовой схемы. Метаданные свежего artifact доступны, но его содержимое
не открывалось; прежнее одноразовое разрешение v180 не покрывает новый restore.
