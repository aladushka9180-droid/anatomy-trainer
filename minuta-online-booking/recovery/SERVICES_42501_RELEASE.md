# Ручное добавление услуги: 42501

## Причина и границы

30.09 повторно прочитаны production metadata. `authenticated` имеет INSERT
на `services` и SELECT на `services.id`, но не EXECUTE на
`minuta_normalize_service_name_v160(text)`. У `anon` этого права также нет.
Функция — SQL IMMUTABLE SECURITY INVOKER с пустым search_path, преобразует
только переданную строку; тело совпадает с v160. Индекс
`services_normalized_name_v160_idx` вычисляет её при прямом INSERT.

Ручная форма: `POST /rest/v1/services?select=id`, поля `performer_id`, `name`,
`price_rub`, `duration_minutes`, `active`, затем возврат `id`. Шаблоны:
`POST /rest/v1/rpc/create_provider_services_from_presets_v160`, сервер сам
получает владельца из `auth.uid()` и сохраняет через SECURITY DEFINER.
Поэтому шаблон работает при отказе ручной формы. Фотография/карточка
выполняются позднее и не вызывают исходный отказ.

Контракт для обсуждаемого объединения интерфейса: RPC принимает и свою
услугу с `preset_id=null`; имя, целая цена 0..1000000 и длительность 5..480
проверяются сервером. Допускается пустой массив профессий для своих услуг,
но выбор профессий при каждом вызове заменяется целиком. Чужой owner в
payload запрещён, владелец берётся из auth.uid(). Подмена прямой формы
этим RPC сейчас нарушила бы поминутный режим (1 минута), могла бы стереть
выбор профессий и не покрыла бы последующее сохранение карточки/фото.
Это оценка контракта, не согласованное изменение интерфейса.

Исходный полный PostgREST message/details/hint не сохранился. История
подтверждает повторные 403/42501 в UI, включая 60 минут; точный текст
`permission denied for function minuta_normalize_service_name_v160`
воспроизведён изолированно, а соответствующие метаданные проверены live.

## Кандидат и доказательства

Исходная правка `fb1435b7` перенесена без изменения в отдельную ветку
поверх свежего main. Только EXECUTE указанной чистой функции для
authenticated; права таблиц, RLS, другие функции и данные не меняются.
Откат отбирает только это прямое разрешение.

PGlite PostgreSQL 17.5: исходная и расширенная проверки PASS.
Расширенная проверка загружает реальную миграцию v160, проверяет ручной
INSERT с/без RETURNING, работающий шаблон до/после, apply дважды,
поминутную услугу, дубликаты, чужие INSERT/UPDATE/DELETE, скрытые услуги,
анонимный доступ, replay, rollback без потери строк и reapply.
Изолированный native PostgreSQL CI дополнительно проверяет две
одновременные вставки одинакового имени. Это синтетическая схема,
не восстановленная production-схема.

Старый `service-presets-ui-static-test.mjs` падает на требовании единой
версии ВСЕХ ресурсов; три входных файла идентичны main v1042. Эта правка
не меняет UI/PWA. Сбой фиксируется отдельно, тест не ослаблен.

## Выпуск единственным владельцем Pro

1. Интегрировать только кандидат этой задачи, проверить текущий main и
   native CI. Не повторять миграцию v160 целиком.
2. Перед применением повторно прочитать function body/owner/ACL, индекс,
   services grants/RLS. Должны совпадать с установленным механизмом:
   чистый invoker-нормализатор, индекс на services, отсутствующий
   authenticated EXECUTE. При расхождении остановить apply и уточнить причину.
3. Отдельный точный допуск пользователя на исправление прав production;
   условный допуск v188/v189 его не покрывает.
4. Свежий закрытый зашифрованный backup + успешная изолированная репетиция
   восстановления по регламенту. Проверить этот grant → rollback → reapply
   на восстановленной схеме; сверить ACL и сохранность строк. Нельзя
   повторять неизменные credentials после authentication_failed.
5. Применить `supabase-services-42501-grant.sql` один раз через
   согласованный канал владельца выпуска. Повторно проверить EXECUTE
   authenticated=true, anon=false; RLS и права таблиц неизменны.
6. В актуальном пользовательском кабинете заново проверить текущий вход,
   открыть «Услуги» → «Добавить услугу», создать одну явно тестовую услугу.
   Подтвердить сохранение после перезагрузки и соседний путь через шаблон.
   Не менять существующую услугу с пользовательского снимка. Не удалять
   контрольную строку без отдельного разрешения.

При ошибке исправления сначала прочитать точный серверный ответ. Откат:
`supabase-services-42501-grant-rollback.sql`; он сохраняет строки, но
возвращает прежний отказ ручного добавления. Production-восстановление
снимка требует самостоятельного точного разрешения и не входит в этот apply.

## Статус

Production grant не применён. Свежий backup, restore и SQL-допуск не
подтверждены. На сайте выполнено 0 из 1; осталось внедрение и живая приёмка.
