# Офлайн-черновики шаблонов и напоминаний: следующий независимый этап

Статус: карта текущего кода и критерии, не реализация и не выпуск.
Сверено 02.10.2026 с public main `594a2fca` (Pro v1065). Общие provider/UI
принадлежат КААРДИНАТОРУ; подготовку офлайн-этапа ведёт владелец очереди.
Каталог v186/v187 интегрируется первым после полного recovery gate.

## Источник и допустимая граница

[Статья Гном.Гуру 2020](https://gnom.guru/ru/Blog/BPage/2518191662820853518)
заявляет офлайн-шаблоны и поздравления. Это заявление поставщика,
не проверка актуального приложения или фактической отправки без сети.
Сценарий Pro: сохранить текст на устройстве, повторно открыть и после связи
сверить с серверной версией. Изменение текста не подтверждает отправку,
создание серверного задания или доставку. Реальные сообщения не разрешены
текущим офлайн-каталожным решением; никакие каналы в этой подготовке не открывались.

## Карта существующих путей

| --- | --- | --- |
| `provider.js`: `saveNotificationTemplates`, `notificationTemplates`, `writeNotificationStorage` | Три текста confirmation/reminder/cancellation записываются в `massage-notifications-<user>-templates`; затем direct upsert `notification_templates` по performer_id. При серверном отказе сообщение говорит о сохранении на устройстве. | Нет expected version/requestID и доказательства replay. `notificationTemplates()` накладывает serverNotificationTemplates поверх local: локальная правка может быть скрыта прежним серверным текстом. Ошибка localStorage сообщает об отказе, но вызывающий save не получает признак успешного local write. |
| `provider.js`: optional settings load и logout | Загрузка читает confirmation/reminder/cancellation; доступность зависит также от policy/marks. Logout сбрасывает серверные переменные. | Локальный ключ зависит от user, не organization. Не считать его готовым контрактом межорганизационных личных шаблонов или подтверждённым удалением локальных данных при выходе. |
| `client-messaging.js`: `loadTemplates`, `saveTemplate`, input и open handler | Личные reminder/reschedule/cancellation используют get/save_provider_message_template_v161, scope organization+performer, version и idempotency key. | `supabase-migration-v161.sql` | Записанный RPC проверяет active membership, serializes writer, сравнивает expected version и хранит только last_idempotency_key. | Совпавший last key возвращает текущую строку без сравнения body запроса. Фактические production функции/grants/RLS ещё нужно сверить, файл SQL не доказывает их текущую установку. |

Локальный черновик правил не активирует серверное расписание. Не создавать неявный повтор настроек после смены аккаунта. |
| `provider.js`: `notificationTaskKey`, marks, `whatsappLink`; `client-messaging.js`: `openChannel` | Marks отдельно записываются/удаляются по performer+task_key; клиентские каналы открываются отдельным действием. | Синхронизация текста не меняет mark «отправлено» и не вызывает openChannel. Копия текста или открытие приложения не равны доставке. |
| v169 reminder catch-up и существующий outbox | Репозиторный сценарий отдельно обрабатывает просроченное напоминание перед началом подтверждённого визита и исключает прошедшее время. | Не добавлять браузерный scheduler/outbox поверх существующего. Авторитетные статус визита, время и право отправки проверяются сервером; в офлайн-подготовке диспетчер не запускается. |

Старые и личные шаблоны имеют разные scope и виды текста. Не объединять
confirmation и reschedule автоматически и не переносить legacy-значение
на всех сотрудников организации. Нельзя дописывать одну общую очередь
«сообщений» для текста, marks, auth settings и отправки: это разные действия.

## Минимальный будущий контракт

- Использовать текущий редактор и существующий серверный путь после сверки
  действительных функций/прав. Новый production SQL требует отдельного gate;
  разрешение v186/v187 его не покрывает.
- Для текста сохранить scope, kind, локальный текст, исходную версию/текст,
  неизменный payload запроса и requestID. Pending удаляется только после
  точного серверного подтверждения; новый ввод сохраняется отдельно от in-flight.
- На конфликте оставить локальный и серверный варианты, дать явный выбор;
  загрузка/повторный вход не должны незаметно заменять локальную правку.
- Legacy local-only значения мигрировать в черновик после подтверждённого
  scope; неизвестную исходную версию не представлять как принятую серверную.
- Ошибка local storage означает «не сохранено на устройстве». Отказ доступа,
  logout или смена организации прекращают отправку и игнорируют поздний ответ.
- Автоматический replay сохраняет только текст. Транспорт, marks, auth settings
  и реальная доставка остаются под своими условиями и отдельными разрешениями.

## Проверяемые критерии будущей приёмки

1. Без сети текст сохраняется, открывается после reload; отказ localStorage
   не даёт ложного «сохранено». Legacy текст и его область не теряются.
2. Потерянный ответ повторяется тем же scope/key/payload. Изменение текста
   во время отправки не теряется при позднем подтверждении прежнего запроса.
3. Два устройства меняют один шаблон: оба варианта доступны, обновление
   сервера не затирается автоматически; повтор после последующей чужой записи
   не объявляется подтверждённым без точного ответа.
4. Logout, смена пользователя/организации и отозванное membership блокируют
   чужой replay; поздний ответ не меняет новый экран или его local state.
5. Синхронизация текста не открывает канал, не выставляет «отправлено» и не
   создаёт новый outbox/cron. Сценарии только на синтетических адресатах,
   без отправок; отдельно сверить будущий reconnect со статусом/временем визита.
6. После последовательной интеграции: профильные CI, ресурс/PWA gate,
   живой авторизованный редактор на 390/760/1440 и безопасная приёмка.
   Физическая Android PWA отдельно; сейчас не проверена.

Следующий безопасный шаг: на изолированных данных воспроизвести потерю
локального текста при version conflict и overlay server/local, затем
спроектировать расширение существующего редактора. Production DDL/grants/RLS,
внешние writer и доказательство живого офлайн-редактора пока отсутствуют.
