# Удаление услуги: кандидат сохранения связанных данных

## Цель и статус
Исправить отказ удаления услуги. Согласованные критерии: (1) подтвердить точную причину пользовательского отказа; (2) проверить правку на изолированных тестовых данных; (3) интегрировать, выпустить и принять целевой live-сценарий. Выполнено 1 из 3; осталось 2: тестовая правка проверена, точный пользовательский отказ и live-выпуск ещё не подтверждены.

## Подтверждённый механизм
На базе свежего `origin/main` 6592ecc2 подтверждён дефект обработчика: он архивирует услугу при SQLSTATE 23503 только для `organization_waitlist_requests`. Миграции v61/v69/v73/v111 содержат другие реальные FK на `services(id)` с RESTRICT/NO ACTION. Изолированный PostgreSQL/PGlite воспроизводит настоящий ответ `update or delete on table "services" violates foreign key constraint` для шести типов ссылок. Исходный обработчик отклоняет пять остальных, исправленный скрывает услугу и сохраняет ссылку.

Это подтверждение механизма в коде и синтетической схеме, а не доказательство причины конкретной ошибки пользователя. В доступной авторизованной вкладке открыт другой кабинет; искомой услуги там нет. Пользовательский PostgREST response body пока не получен. Production RPC не определён в репозитории, его тело не читалось. Анонимный запрос с несуществующим UUID лишь подтвердил наличие защищённой функции, вернув 401/42501; этот ожидаемый отказ не является причиной пользовательской ошибки.

## Состав и сохранённые границы
- `service-delete-history.patch`: узкая правка общего обработчика и адаптация прежнего теста к фильтру владельца. Общий `provider.js` в рабочем checkout не изменялся: его владельцем остаётся «КААРДИНАТОР».
- `tests/service-delete-history-test.mjs`: подтверждение настоящих FK-ответов на минимальной схеме с FK-определениями из миграций, сравнение исходного и исправленного обработчика.
- `.github/workflows/service-delete-history.yml`: изолированная CI-проверка кандидата и итогового обработчика; ни доступа к production, ни production SQL.

Fallback ограничен 23503 при удалении именно из таблицы `services`; сохраняется прежний waitlist-случай. Другие FK, ошибки прав, транспорта и RPC не превращаются в успешное скрытие. UPDATE ограничен ID услуги и текущим владельцем; успех требует возвращённых правильного ID и `active=false`. При скрытии остаются фото, короткое название и связанные строки. Штатное успешное удаление сохраняет прежнюю очистку.

## Единственный владелец выпуска
Пользователь прямо разрешил передачу кандидата в чат «КААРДИНАТОР». Этот чат остаётся единственным владельцем общего обработчика, версий, main и публикации; текущая задача не делает конкурирующий выпуск.

1. Сверить точную пользовательскую ошибку и целевой кабинет. Если отказ иной, не считать этот кандидат исчерпывающим исправлением.
2. Перенести кандидат в изолированную integration copy свежего main, применить `git apply minuta-online-booking/recovery/service-delete-history.patch`. При расхождении контекста переносить только эту логику; не перезаписывать новый код main.
3. Запустить новый тест с `MINUTA_PGLITE_PACKAGE` и `--integrated`, прежний waitlist-тест, syntax и обязательные проверки общего обработчика. Присвоить текущую свободную версию ресурсов, проверить redirect перед push, exact CI и Pages.
4. Проверить фактически загруженный обработчик и согласованный сценарий на live. Не удалять рабочую услугу или историю пользователя для доказательства без отдельного точного подтверждения; использовать согласованные тестовые данные. Связанная услуга скрывается, а физическое удаление остаётся защищено ссылками.

Production SQL, изменения прав/RLS, удаление реальных записей и самостоятельная публикация этим кандидатом не выполнялись и не требуются.
