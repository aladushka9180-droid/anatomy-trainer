# v184: защищённый пакет выпуска удаления записи

Статус: подготовлен локально, production не читался и не изменялся на этом этапе. Владелец интеграции и выпуска — КААРДИНАТОР. Пакет не запускает удаление записи; повторная штатная мобильная проверка возможна только после принятого выпуска. UI не является зависимостью SQL-исправления.

SQL/RPC не менялись после native PASS.

## Порядок выпуска после отдельного разрешения

1. Интегрировать пакет под одним владельцем; зафиксировать точный свежий main SHA. v182/v183 заняты лояльностью, v184 зарезервирован этому исправлению.
2. `eldion-booking-delete-release.yml`, `validate-production`: только read-only проверки целевой БД, оригинального RPC, RLS и прав. Это фаза по умолчанию.
3. Новый штатный зашифрованный backup на том же SHA; затем `minuta-supabase-restore-drill.yml`, target=ephemeral, candidate_version=v184, candidate_sha=commit_sha, точный backup_run_id. Production-копия восстанавливается только на runner в PostgreSQL 17 с network=none; apply→rollback→reapply, затем контейнер и расшифрованные файлы удаляются.
4. `apply-production`: точные IDs validation/backup/restore и `APPLY_V184_AFTER_BACKUP_RESTORE`. Все runs должны успешно завершиться на том же main; backup не старше двух часов повторно проверяется непосредственно перед SQL. Общая concurrency `minuta-production-database`, защищённая environment `minuta-production`. По умолчанию соединения read-only; write включается только у единственного psql с проверенной транзакцией.
5. `observe-production`: отдельная read-only проверка нового RPC/архивной схемы и artifact успешного apply. Затем одна разрешённая попытка удаления целевой записи штатной кнопкой, свежая синхронизация и проверка истории. Другие реальные записи не трогать.

Пока никакой из новых production/backup/restore workflows не запускался. После любой ошибки или неоднозначного ответа применения сначала выяснить состояние, не повторять apply/удаление вслепую. Замена main требует новой цепочки доказательств. Старые v177/v180/v181 ветви восстановления сохранены.

## Что гарантирует оболочка

В одной транзакции берутся SHARE-блокировки проверяемых таблиц записей/отзывов/платежей/событий/сессий/членства и всех message/conversation v162 таблиц. До и после SQL сравниваются число и отпечаток полных строк; новый `deleted_booking_id` исключается только при NULL, ненулевой исторический UUID входит в сравнение. Неизменность владельцев/ACL/RLS/policies, прочих функций, FK и триггеров проверяется отдельно. Ожидание блокировок ограничено 5 сек.; отдельного SQL — 5 мин. Запись в связанные таблицы может кратковременно ожидать завершения транзакции. При расхождении COMMIT не выполняется. Приватные строки/отпечатки не экспортируются.

Обычный backup/restore намеренно не переносит ACL. Только в offline-клоне до baseline восстанавливается проверенный контракт этого RPC: EXECUTE для authenticated, без PUBLIC/anon/service_role. Это явно отмечено `rpcAclReconstructed:true`; не выдаётся за восстановление оригинальных прав из backup. В production реальные права проверяются read-only и сравниваются внутри самой транзакции. Native тест клонировал схему с её ACL отдельно.

## Точное воздействие для одного согласования

Разрешение требуется на свежую зашифрованную резервную копию, её временное восстановление на изолированном runner, read-only проверки и применение ровно v184 к рабочей БД. Само применение добавляет два nullable UUID, два совместимых CHECK и меняет одну функцию; существующие записи, сообщения, авторы, участники и история сохраняются. Удаление из workflow не вызывается.

При последующем удалении выбранной записи связанный клиентский диалог сохраняется для чтения, отправка закрывается. Участник по ссылке на эту запись становится неактивным; гостевая сессия, привязанная к удалённой записи, прекращается по существующему CASCADE. Аккаунт клиента и сотрудники сохраняют прежний доступ к истории; посторонним он не открывается. Связанный диалог поддержки не закрывается. Остальные запреты удаления, включая отзывы и финансовые/другие RESTRICT-связи, остаются.

Откат возвращает прежнюю функцию v64, сохраняя добавленные архивные поля/проверки и уже отделённую историю. Он не восстанавливает удалённую запись. Rollback SQL и его оболочка подготовлены и проверены на изолированных данных; автоматического production-отката или восстановления нет.

Незакрытые ворота: интеграция владельцем, отдельное разрешение пользователя на эту цепочку, фактический backup/offline rehearsal на точном main, apply/observe, штатная проверка одной целевой записи. Установленный Android не проверен.
