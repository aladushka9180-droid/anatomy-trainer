# Следующий независимый этап: заметки клиента

Статус: подготовлен план, без реализации и выпуска. Сценарий №2 общей
офлайн-очереди; текущий этап каталога v186/v187 остаётся первым для интеграции.
Источник Гном.Гуру заявляет доступ к прежним данным; отдельная офлайн-запись
заметок и актуальное поведение Android-приложения не доказаны.

## Подтверждённый код и граница подготовки

На свежем `origin/main` `6592ecc2fb4b6f0eabd35eb94e940886fb71abd5` функция
`saveClientNoteValue` в `provider.js` использует существующие `pendingClientNotes`,
ключ `massage-client-notes-pending-v1:<user>` и последовательные очереди записи
по пользователю, поколению сеанса и телефону. В запросе прямого `client_notes`
upsert есть текст и время браузера; ожидаемая серверная версия и request ID
не передаются. Это чтение исходника, не доказательство состояния рабочей БД.

Текущее хранилище и очереди сохранять. Общий `provider.js` принадлежит владельцу
выпуска; его не менять параллельно. Existing metadata/adversarial проверки
проверяют настоящие helper-функции на синтетическом транспорте и имеют свои
ограничения; они не доказывают серверный конфликт двух устройств.

## Карта действующих путей на v1064

Поиск в JS/MJS/TS/SQL репозитория показал один прямой upsert текста заметки
в `saveClientNoteValue` и отдельное изменение её идентичности в SQL v134.
Это карта исходника; внешние writer и права рабочей БД пока не подтверждены.

| Путь | Действующий источник | Требование следующего этапа |
| --- | --- | --- |
| Карточка клиента | `saveClientNote` → `saveClientNoteValue` | Версия, request ID, сохранение локального и серверного текста при конфликте |
| Заметка из карточки визита | `saveBookingSheetNote` → тот же helper | Сохранить контекст формы и телефона при позднем ответе |
| Создание обычной записи, серии и визита в прошлом | Три ветви `createNewBooking` → тот же helper | Конфликт заметки после принятия визита не должен повторять создание визита |
| Завершение опубликованной офлайн-очереди записи | `finalizeQueuedBooking` → тот же helper | Конфликт заметки не теряет уже созданный визит и не создаёт дубликат |
| Повтор pending-заметок | `flushPendingMetadata` → helper с `replay:true` | Использовать исходные базовую версию и request ID |
| Загрузка и обновления | `loadClientNotes`, realtime `client_notes` | Загружать подтверждённую версию отдельно от локального pending |
| Смена телефона | `save_minuta_client_identity_v134`, `applyClientIdentityLocally` | Согласовать перенос серверной заметки, pending и незавершённого запроса |

`loadClientNotes` сейчас выбирает только `client_phone,note` и накладывает
pending поверх серверного текста; базовый вариант отдельно не хранится.
SQL v134 меняет `client_notes.client_phone` без присваивания `updated_at`,
а локальный перенос меняет ключ pending. Очередь helper привязана к прежнему
телефону, поэтому перенос и поздний запрос нужно проверить причинным сценарием,
а не считать безопасными по клиентской последовательности.

DDL, действующие grants/RLS и все внешние writer `client_notes` по этому поиску
не установлены. Получить их с полного CURRENT стенда через того же владельца;
не подменять неизвестную рабочую схему синтетической.

## Предлагаемый минимальный контракт

- Область прежняя: личная заметка исполнителя по нормализованному телефону.
  Подготовка не расширяет доступ других сотрудников или организаций.
- До отправки сохранить текст, подтверждённую базовую версию, request ID и
  контекст аккаунта в существующем механизме pending. Время браузера само по
  себе не является серверной версией.
- Устаревшая база должна оставлять локальный текст и актуальный серверный
  вариант для решения пользователя. Автоматическое объединение или перезапись
  чужой правки не предусмотрены предлагаемым контрактом.
- Повтор одного запроса не создаёт вторую запись. Тот же ID с другим текстом
  отклоняется. Если после принятия запроса серверная заметка изменилась,
  повтор не изображает прежний текст актуальным.
- Старые pending-строки v1 без базовой версии не удалять и не дополнять
  придуманной версией: они требуют отдельной сверки перед записью.
- Все пути заметки, включая обычное онлайн-сохранение, импорт и смену телефона,
  должны быть сверены с новым контрактом. Частичное переключение одного writer
  не считается защитой всех заметок от перезаписи.

## Критерии будущей проверки

1. Два устройства одного исполнителя: устройство A сохраняет локальный B
   на базе текста A; устройство B подтверждает C. Отправка B с прежней базой
   получает конфликт, серверный C и локальный B сохраняются.
2. Принятый запрос с потерянным ответом повторяется с тем же ID: одна запись
   и один результат. Последующая правка C не скрывается старым replay.
3. Другой исполнитель, смена аккаунта, выход и ответ старого сеанса не дают
   доступа и не восстанавливают очищенные локальные данные.
4. Новый текст во время незавершённой отправки не удаляется ответом старого
   запроса. Смена телефона не переносит запрос на неизвестную идентичность.
5. Перезагрузка, отказ localStorage и старые pending v1 сохраняют честный
   статус; неизвестный результат не показывается сохранённым.
6. Серверная смена телефона одновременно с незавершённой заметкой не создаёт
   заметку по прежнему телефону и не теряет pending; replay принятого до переноса
   запроса не восстанавливает прежнюю идентичность.
7. Конфликт заметки в `finalizeQueuedBooking` и ветвях создания оставляет один
   уже подтверждённый визит. Работа опубликованной очереди записи сохраняется.

Проверять сначала на изолированной схеме и синтетических клиентах с настоящими
writer/RLS, затем на полном восстановленном контуре. UI, живой сценарий и
физическая Android PWA принимаются отдельно. Новые production SQL, доступы и
рабочие заметки не разрешены разрешением только v186/v187; номера будущих
миграций назначаются после сверки свежего main и отдельного допуска.

Следующий шаг после каталога: сверить все writer с действующим владельцем,
выбрать совместимый контракт и подготовить причинные PostgreSQL-проверки.
