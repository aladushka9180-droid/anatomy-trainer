# Гибкое офлайн-время v178 / PWA v939: план защищённого выпуска

Статус: локальный кандидат, не применён к production и не опубликован. Владелец
интеграции пакета — задача в worktree `f4d7`; перед выпуском она сверяет свежий
`origin/main` и подтверждает единственного владельца полосы выпуска. SHA
кандидата и SHA `main` фиксируются заново перед каждым внешним шагом.

## 1. Снимок базы — отдельное разрешение

- Источник: production PostgreSQL по секрету `SUPABASE_DB_URL` в окружении
  `minuta-production`. Ручной `Minuta Supabase encrypted backup` запускается на
  точном SHA `main`, с `destination=github-artifact-only`. Команда `pg_dump`
  создаёт полный доступный custom archive схемы и строк БД без владельцев и ACL.
  Он может содержать персональные данные и метаданные Auth/Storage; сами файлы
  Storage, Edge-секреты и внешние сообщения в архив не входят.
- Место: зашифрованный `.dump.gpg` вместе с SHA-256 и журналом в GitHub Actions
  artifact репозитория `aladushka9180-droid/anatomy-trainer`, имя
  `minuta-YYYY-MM-DDTHH-MM-SSZ`, срок 35 дней. S3 при этом выборе не используется.
  GPG AES-256 берёт существующий секрет `BACKUP_ENCRYPTION_PASSWORD`; пароль не
  запрашивается у пользователя и не выводится. GitHub автоматически удаляет
  artifact по сроку; досрочное удаление не входит в этот план.
- Проверка на runner: `pg_restore --list`, расшифровка, побайтовое сравнение
  plaintext и расшифрованной копии, SHA-256 и журнал. Временные plaintext
  архивы удаляются trap; runner уничтожается GitHub. Если доступ, конфигурация,
  место на runner или любая проверка не проходит, остановиться без SQL.
- Текущий фактический размер дампа, значение прежней переменной S3 и доступность
  секретов не подтверждены: `gh` для переменных/секретов возвращает HTTP 401.
  До запуска сверить доступ к защищённому workflow и точное назначение.

## 2. Восстановление и репетиция — то же отдельное разрешение

- Ручной `Minuta monthly restore drill`: `restore_target=ephemeral`, точные
  `backup_run_id` и `commit_sha` снимка, `candidate_version=v178`, точный
  `candidate_sha` просмотренного SQL. Job требует `minuta-production`; источник
  должен быть успешным ручным backup моложе 24 часов на актуальной линии main.
  Кандидат должен происходить от SHA снимка, checkout берёт только v178 SQL и
  rollback SQL.
- Dump расшифровывается только на runner. Скрипт восстанавливает `public`
  schema/data в одноразовый PostgreSQL 17 Docker с `--network none`, создавая
  лишь инертные Auth UUID-заглушки. Реальные Auth-строки, Storage-метаданные и
  Storage-файлы в тестовую БД не восстанавливаются. В `public` при репетиции
  всё же находятся реальные персональные строки, поэтому контейнер изолирован
  и удаляется по завершении; приватный лог и plaintext архив удаляются.
- На восстановленной схеме проверяются v178 apply, наличие RPC/ledger и число
  записей, rollback с сохранением ledger/записей и повторный apply. Отчёт
  содержит только агрегаты и булевы флаги, без строк клиентов; artifact отчёта
  хранится 35 дней. Любой сбой останавливает выпуск. Никакой production SQL в
  этом job не выполняется.

## 3. Отдельные gates после успешной репетиции

1. Только после отдельного точного разрешения применить
   `supabase-migration-v178.sql` к production одним владельцем выпуска. Перед
   применением повторно сверить SHA, свежесть backup, результат restore, тела
   затронутых RPC/constraint и отсутствие новой коллизии миграции.
2. После проверки production RPC интегрировать UI/PWA v939 в `main` обычным push
   без force и дождаться CI/Pages. Затем проверить точные HTML/JS/CSS/SW байты,
   обновление кэша и реальный экран 390/760/1440 на рабочем сайте без создания
   реальных записей или сообщений. Установленная Android PWA требует отдельной
   проверки на устройстве и не подтверждается браузерным тестом.

## Откат

- Ошибка применения v178 внутри транзакции откатывает миграцию автоматически.
  Если дефект обнаружен после применения, штатный
  `supabase-migration-v178-rollback.sql` удаляет только новую RPC и её EXECUTE;
  ledger и уже созданные записи сохраняются. Перед этим, если UI уже вышел,
  вернуть прежние UI/PWA ресурсы обычным выпуском с новой версией кэша, чтобы
  клиенты не продолжали вызывать удалённую RPC. Очереди на устройствах не
  очищать автоматически и не отправлять повторно без проверки.
- Восстановление production из dump — отдельная опасная операция и не входит
  в разрешение на репетицию или SQL v178. При необходимости нужен новый план с
  точным состоянием данных и отдельное разрешение.
