# Кандидат: удаление записи с сохранением диалога

## Подтверждённая причина

Единственный разрешённый read-only запуск 36478633219 (main e0d443218567815ada059b29fc532359865694b1) нашёл две блокирующие связи: `message_conversations_v162.primary_booking_id` и `message_participants_v162.booking_id`, по одной строке, обе ON DELETE RESTRICT. Отзывов, платежей и действий-сообщений у целевой записи нет. Рабочая функция удаления — v64; authenticated может её вызвать, владелец postgres имеет BYPASSRLS. Одна разрешённая штатная мобильная попытка дала отказ; после новой синхронизации запись осталась.

## Изменение

- `booking-delete-dialog-candidate.sql`: два nullable UUID-поля исторической ссылки, точечная замена двух identity CHECK и новая реализация существующего RPC. Номер миграции назначает единственный владелец выпуска после проверки общей очереди; v182/v183 заняты другими кандидатами.
- При применении SQL записи, диалоги и сообщения не удаляются. При последующем штатном удалении владелец блокирует выбранную запись, проходит прежние проверки прав/отзыва и отделяет только её от диалога и booking-client участника. Сообщения, авторы, события и аудит сохраняются.
- Связанный клиентский диалог становится доступен для чтения, отправка закрывается. Участники-сотрудники и аккаунт клиента сохраняются; функции доступа и чтения не изменены. Поддержка не закрывается автоматически.
- Участник, существующий только по удаляемой записи, остаётся автором истории, но становится неактивным. Сессии по ссылке на запись уже имеют ON DELETE CASCADE в v155; кандидат не продлевает их доступ. Это важно явно включить в описание воздействия перед разрешением выпуска.
- Все FK RESTRICT остаются, включая действия-сообщения, финансовую/другую историю. Если другая связь запрещает удаление, изменения диалога, участника и платежей атомарно откатываются. Этот пакет устраняет две подтверждённые связи, а не снимает остальные защиты.
- Проверяется отпечаток исходной/кандидатной функции; неизвестная функция либо чужие колонки приводят к отказу миграции.

Прежний диалог остаётся читаемым, соседняя запись не меняется. На 29 сентября проверены существующие environment `minuta-test`, concurrency `minuta-test-database`, migration-config-guard и marker; текущий integration run 36482339520 успешно прошёл guard и запросы к отдельной тестовой базе. Локальные тестовые секреты не извлекались. Свежий origin/main: 62ade258a3d92b2cdb5dae5a8c6a17f379d4e38b; v64/v155/v162 и общий fixture относительно ветки не менялись.

Готов `.github/workflows/eldion-booking-delete-isolated.yml`, по образцу существующего v181 gate. Он читает **только public-схему** из проверенной тестовой базы через pg_dump --schema-only, сохраняя ACL; строки клиентов/платежей/переписки не копируются. Production secret не используется. Исходная test database не изменяется. Перед импортом существующий строгий фильтр исключает outbound webhook triggers. Bootstrap auth.users содержит только поля синтетического fixture; auth.uid/role/jwt — стандартные тестовые функции, это не доказательство managed Auth/Storage. Приложение проверяется на полной public-схеме из test, не на сокращённом DDL PGlite.

Клон — новый PostgreSQL 17 service с фиксированным отдельным именем базы и localhost-портом. В нём выполняются full-schema и concurrency; private schema/logs удаляются, сервис уничтожается после job. YAML, все shell-блоки и защитные условия локально проверены; это **не runtime PASS**. Перед запуском координатор проверяет наличие v155/v162 и исходного v64 в тестовой схеме; guard кандидата останавливает несовместимую версию. Владелец интеграции запускает CI после приёмки локального коммита; исполнитель push/main и dispatch не выполнял.

## Откат

`booking-delete-dialog-rollback.sql` возвращает канонический RPC v64. Дополнительные колонки и расширенные CHECK остаются, чтобы сохранить уже отделённую историю. Повторный откат безопасен; повторное применение кандидата проверено. Это откат поведения, а не восстановление удалённой записи. Полный возврат прежней схемы после успешного удаления нельзя делать с потерей архива.

## Перед выпуском

1. Владелец выпуска сверяет свежий main, номер миграции, права и семантику закрытия диалога. Отдельный фронтенд-патч try/catch/finally не является исправлением этого FK-отказа.
2. Запустить полный изолированный сценарий, доказать гонки удаления/отправки/новой связи, свежий backup и восстановление по действующему регламенту. Не переносить synthetic PASS на production.
3. Получить отдельное разрешение на конкретное production-изменение базы. Разрешение удалить одну запись штатной кнопкой уже есть, но не заменяет разрешение на SQL.
4. Один выпуск, затем одна осмысленная повторная попытка удаления согласованной записи через мобильный интерфейс, проверка свежей серверной синхронизации и сохранности переписки. Другие реальные записи не трогать.

## Текущий блокер

Runtime full-schema/concurrency ожидают приёмки коммита и одного запуска CI владельцем выпуска. Местных PostgreSQL/psql/docker и TEST_DATABASE_URL нет; действующий изолированный CI-контур найден и проверен по последнему успешному запуску.

Автоматическая передача через send_message_to_thread ранее дважды отклонена: инструмент требует approval при policy=never. Отказы не повторялись и не обходились. Координатор самостоятельно забрал кандидат разрешённым чтением и поручил подготовку отдельного теста/коммита; прежний отказ передачи теперь не блокирует приёмку. Production SQL не применялся, повторного реального удаления не было. Физический Android не проверен.
