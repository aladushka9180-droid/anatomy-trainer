# Минута — онлайн-запись

Онлайн-запись для GitHub Pages с общей базой Supabase. Клиенты выбирают услугу и свободное время, а исполнители регистрируются, добавляют свои услуги и управляют заявками в отдельном кабинете.

Доступ к данным ограничен политиками Row Level Security: клиент не может читать чужие записи, исполнитель видит только свои услуги и заявки.

## Надёжность

- Кабинет подписывается на изменения записей, услуг, графика и исключений через Supabase Realtime и дополнительно сверяется с сервером раз в пять минут, пока открыт и доступен интернет. После восстановления соединения загружает пропущенные изменения.
- Журнал, услуги и расписание загружаются первыми; оформление записей, уведомления и дополнительные разделы не задерживают готовность журнала. При сбое основного этапа дополнительные запросы не запускаются.
- Запросы чтения таблиц и явно перечисленных безопасных RPC ограничены 12 секундами на попытку, включая получение тела ответа. Допускается одна повторная попытка; сохранения, платежи, удаление и авторизация этим механизмом не повторяются. Выход из аккаунта отменяет ожидающие чтения.
- Недавние записи, услуги и расписание сохраняются в IndexedDB не дольше 7 дней, доступны только для чтения при сбое связи и очищаются при явном выходе; офлайн-копия записей включает имена и телефоны, чтобы расписание владельца оставалось полноценным без связи.
- Изменения в кабинете разрешаются только после успешной полной синхронизации; ответы от предыдущей пользовательской сессии отбрасываются.
- Страница клиента показывает, проверена ли возможность записи, и не выдаёт сетевую ошибку за успешно созданную заявку.
- При двух и более исполнителях клиент может отфильтровать услуги по специалисту; при одном исполнителе лишний шаг автоматически скрыт.
- Owner/admin могут переключить существующий журнал в read-only командный режим и фильтровать записи по филиалу, специалисту и назначенному ресурсу; командные ПДн не пишутся в офлайн-кэш.
- В контуре v69 owner/admin настраивают кабинеты, массажные столы и оборудование по филиалам; база атомарно назначает свободные ресурсы и блокирует их двойное бронирование.
- Исполнитель может атомарно создать курс из 2–24 визитов и затем перенести или отменить одну запись, выбранную и последующие либо все будущие записи серии. Если хотя бы одно окно занято, вся операция откатывается.
- Создание записи идемпотентно: повтор после обрыва связи использует тот же UUID, возвращает первоначальный результат и не создаёт дубль.
- Клиент может открыть персональную страницу управления записью сразу после подтверждения.
- Если свободного времени нет, клиент может оставить заявку в листе ожидания и управлять ею по личной ссылке.
- На странице управления записью клиент может подтвердить визит кнопкой «Да, я приду».
- Ограничения отмены и переноса проверяются на сервере; исполнитель настраивает сроки и максимальное число переносов.
- Можно включить предоплату: клиент получает персональную платёжную ссылку, а исполнитель отмечает статус в кабинете.
- Слой v87 подключает ЮKassa через изолированные Edge Functions: создание платежа, проверка webhook, сверка статуса, полный и частичный возврат идемпотентны. Для каждой организации эквайринг изначально выключен; тестовые или рабочие ключи хранятся только в Supabase Secrets.
- Автоматически завершённые после рабочего дня визиты отмечаются оплаченными на полную стоимость и сразу учитываются в статистике; результат можно исправить вручную.
- Для услуг длительностью 1 минута цена считается тарифом за минуту; после визита мастер указывает фактическое время и получает итоговый расчёт.
- В каждой записи можно изменить состав сеанса, добавить каталожные или произвольные услуги и сохранить историю первоначальной и итоговой стоимости без изменения каталога.
- Шаблоны уведомлений и отметки об их отправке синхронизируются между устройствами через Supabase.
- Слой v88 расширяет существующий outbox до единого центра Telegram, email, SMS, MAX и push для команды и клиентов. Общий выключатель и каждый канал изначально выключены; без подтверждённого адреса, согласия клиента и настроенного шлюза сообщение не отправляется.
- Владелец может безопасно находить клиентов после перерыва: предложение готовится только при отдельном согласии, а период защиты блокирует частые повторы.
- Слой v89 позволяет владельцу организации добавить в карточку клиента собственные поля: текст, комментарий, число, дату, переключатель или список. Функция изначально выключена, записи из другой организации недоступны, а специалист видит значения только клиентов из своих записей.
- Слой v90 связывает подтверждённый номер Supabase Auth с существующей карточкой клиента и выдаёт совместимую с прежним кабинетом сессию. Клиентские OTP-регистрации не создают пустой кабинет исполнителя, а вход исполнителя по SMS разрешён только для ранее привязанного номера.
- Слой v91 подготавливает единый вход через Telegram, VK ID и Яндекс ID. Исполнитель привязывает внешний аккаунт из действующего кабинета, а клиент подтверждает существующий профиль телефоном и личным кодом; конфликтующая связь отклоняется без создания дубля. Провайдеры остаются выключенными до добавления их секретов в Supabase Auth.
- Слой v92 сохраняет источник создания записи и роль автора без изменения действующих RPC, а также добавляет защищённую аналитику команды по плановой, выполненной и оплаченной выручке.
- Слой v93 ведёт неизменяемую историю создания, переноса, отмены, восстановления, смены услуги или сотрудника, результата визита и оплаты. Участник команды видит только разрешённую ему область организации.
- Слой v94 добавляет постраничный защищённый отчёт по записям сотрудников с фильтром исполнителя и явным списком разрешённых полей.
- Слой v95 импортирует клиентскую базу из CSV-выгрузок YCLIENTS, DIKIDI, Masters и других систем. Дубли объединяются по нормализованному телефону, импорт доступен только владельцу и администратору, а исходные согласия не додумываются.
- Слой v96 исправляет составную стоимость, multi-org аналитику и конкурентно строит индексы длинной истории.
- Слой v97 фиксирует исторического исполнителя завершённого визита, считает доступное рабочее время, выдаёт отчёты и журнал постранично и сохраняет снимки истории после удаления записи.
- В кабинете есть персональный операционный помощник: он поддерживает приветствия, благодарности, вопросы вроде «как дела?», короткие реакции «да», «нет» и «продолжай», а затем естественно переводит разговор к рабочей задаче. По одной русской голосовой или текстовой команде он показывает расписание, свободные окна, клиентов, выручку, уведомления и склад; готовит дневную сводку, безопасный черновик записи, сообщения клиентам, ответы на отзывы, описания услуг и публикации; предлагает проверяемые сценарии цены и продвижения; открывает нужный раздел кабинета. Перенос и отмена записи начинаются с наглядного предпросмотра «было → станет» и открывают штатную форму с отдельным подтверждением. Помощник учитывает роль сотрудника, показывает свежесть источника и позволяет сразу исправить неверно понятую команду без сохранения текста. Он исправляет частые опечатки и ошибки распознавания речи, показывает внесённые исправления и принимает короткие уточнения. Для сложных и контекстных фраз предусмотрен защищённый серверный ИИ-разбор со строгой JSON-схемой, динамическим словарём услуг и записей и повторной локальной проверкой результата; без настройки внешней модели остаётся локальный fallback. Тексты можно скопировать, а изменения данных всегда остаются за защищённой формой и явным подтверждением пользователя. Офлайн помощник использует существующую обезличенную копию не старше 7 дней, сообщает время обновления и перепроверяет свободное время после восстановления связи. На мобильных устройствах поддержан Web Speech и безопасный переход к системной диктовке клавиатуры. В самом помощнике можно выбрать установленный русский голос, настроить скорость и сразу прослушать пример; выбор хранится только на текущем устройстве. Настройка ИИ-контура описана в `supabase/ASSISTANT_AI_SETUP.md`.
- Service Worker использует единый номер сборки и не подменяет отсутствующие JavaScript-файлы HTML-страницей.
- Supabase SDK закреплён локально с SRI-проверкой, а CSP разрешает соединение только с используемым проектом.
- Портфолио синхронизируется между телефоном и ПК: мастер загружает фото «до» и «после», отдельно указывает число сеансов и меняет порядок перетаскиванием либо кнопками.
- Исходные изображения преобразуются в WebP без EXIF; файлы хранятся в закрытом Storage, а публикация возможна только после подтверждения согласия клиента.

Проверка перед публикацией:

```bash
node minuta-online-booking/smoke-test.mjs
node minuta-online-booking/voice-assistant-test.mjs
node minuta-online-booking/assistant-ai-static-test.mjs
```

Изолированная runtime-проверка миграции и обоих вариантов отката v113 использует закреплённую версию PGlite:

```bash
npm install --no-save --ignore-scripts @electric-sql/pglite@0.5.8
node minuta-online-booking/tests/profitability-v113-pglite-runtime-test.mjs
```

Если пакет уже находится вне рабочего дерева, путь до его `dist/index.js` можно передать через `MINUTA_PGLITE_MODULE`; `node_modules` в репозиторий не добавляется.

Проверка уже опубликованного сайта и публичных RPC:

```bash
node minuta-online-booking/production-health-check.mjs
```

Миграции `v41`–`v64` являются неизменяемой историей, а v64 остаётся последним определением защищённого удаления. Слои v65–v78 последовательно добавляют организации, команду, филиалы, ресурсы, аватары, смены, зарплаты, клиентские продукты, наблюдение за публичной страницей, цвета, политики записи, защищённые Telegram-напоминания и Realtime-готовность услуг. v79–v86 аддитивно добавляют серии и пакеты записей, групповые события, лояльность, склад, безопасный возврат клиентов, взаимную исключаемость выгод и корректный порядок проверки групповых пересечений. v87–v91 добавляют выключенные по умолчанию ЮKassa, единый центр уведомлений, настраиваемые поля клиентов, телефонную и внешнюю идентификацию. v92–v94 добавляют атрибуцию, аналитику, журнал изменений и постраничный отчёт. v96 исправляет критические контракты и индексы, v95 добавляет безопасный импорт, v97 — исторические снимки и аналитику сотрудников. Безопасный порядок хвоста: v92 → v93 → v94 → v96 → v95 → v97. Эти слои не заменяют защищённые RPC v61/v64/v76. Точный порядок описан в `OPERATIONS.md`, `SAFE_RELEASE.md` и `SOCIAL_AUTH_SETUP.md`.

Настройка мониторинга, уведомлений, резервных копий и отдельного тестового проекта описана в `OPERATIONS.md`.
