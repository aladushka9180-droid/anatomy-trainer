# Безопасный выпуск PrimeTime Pro

Миграции v41–v64 считаются неизменяемой историей. Каноническая v64 остаётся последним определением безопасного удаления. После v64 хвост выпуска применяется как v65–v94, затем v96, v95 и v97. v92–v94 добавляют атрибуцию, командную аналитику, журнал и постраничный отчёт; v96 исправляет стоимость составных сеансов, multi-org аналитику и создаёт индексы без блокировки записи; v95 добавляет дедуплицированный импорт; v97 фиксирует исторического исполнителя, доступное время и сохраняемые снимки событий. Эти слои не переопределяют RPC v61/v64/v76.

## Выпуск

1. Зафиксировать SHA коммита, версию ресурсов и перечень миграций.
2. Запустить `Minuta safe release gate` в режиме `test-migration`. Он повторно применяет v65–v94, v96, v95 и v97, проверяет tenant-backfill, изоляцию календаря и ресурсов, конкурентные пересечения, аналитику, сохранение журнала после удаления записи, импорт клиентов, индексы истории, обратные миграции и неизменность защищённых RPC.
3. В тестовой базе выполнить сценарии из `PAYMENT_FOUNDATION.md`, проверить выключенное состояние v87–v89, идемпотентный повтор операций, ограничения ролей, очередь/повтор уведомлений и типы дополнительных полей. Production для платёжных и конкурентных испытаний не использовать.
4. Только после успешного `test-migration`, откатываемой проверки production и проверенной свежей резервной копии одним выпуском применить v64–v94, v96, v95 и v97. В `production-migration` передаются ID всех трёх запусков. Production-исключений без backup нет.
5. Интерфейсы серий и v87–v97 публиковать только после успешной установки соответствующих RPC: старый интерфейс совместим с новой схемой, но новый интерфейс не должен опережать миграции.
6. Сразу выполнить production health check.
7. Запустить `Minuta safe release gate` в режиме `observe-production` на 30 или 60 минут. Проверка только читает опубликованные страницы и публичные RPC.
8. Записать SHA, время, результаты миграции, health check и наблюдения в журнал выпуска.

Workflow ничего не публикует автоматически. Фаза `production-migration` запускается только вручную и требует отдельную строку подключения production, ID успешных `test-migration`, `validate-production-rollback` и свежего backup; до этих подтверждений запуск запрещён. Rollback-файлы v92–v97 являются test-only и могут удалять тестовые данные. Для фазы `test-migration` секрет `MINUTA_TEST_DATABASE_URL` должен вести только в изолированную тестовую базу. В environment `minuta-test` также нужны variables:

- `MINUTA_PRODUCTION_PROJECT_REF` — ref рабочего Supabase;
- `MINUTA_TEST_PROJECT_REF` — другой ref тестового Supabase;
- `MINUTA_TEST_MIGRATION_CONFIRM=MIGRATE_ONLY_ISOLATED_TEST_DATABASE`.

Один раз создать в тестовой базе защитный маркер, подставив её фактический ref:

```sql
create schema if not exists minuta_migration_guard;
revoke all on schema minuta_migration_guard from public, anon, authenticated;
create table if not exists minuta_migration_guard.target (
  project_ref text primary key,
  allow_migrations boolean not null default false
);
insert into minuta_migration_guard.target(project_ref, allow_migrations)
values ('TEST_PROJECT_REF', true)
on conflict (project_ref) do update
set allow_migrations = excluded.allow_migrations;
```

Перед SQL workflow сверяет строку подключения, разные project ref, точную фразу-разрешение и этот маркер. При любом несовпадении миграции не запускаются.

## Безопасная активация v87–v89

- Сразу после миграции `organization_payment_provider_settings.enabled`,
  `organization_notification_settings.enabled`, все строки
  `organization_notification_channels.enabled` и
  `organization_client_field_settings.enabled` должны оставаться `false`.
- ЮKassa сначала включается только в тестовом режиме после установки секретов
  Edge Functions. Переключение на production и фискализацию выполняется отдельно
  после успешного тестового платежа, webhook, сверки и возврата.
- Единый центр уведомлений включается после настройки dispatcher. Каждый канал
  включается отдельно только при наличии подтверждённого endpoint и основания
  согласия; включение общего переключателя не должно активировать каналы само.
- Дополнительные поля включаются владельцем организации отдельно. Их отсутствие
  или ошибка загрузки не должны блокировать карточку клиента и операции записи.
- После активации или появления платёжных/уведомительных журналов destructive
  rollback запрещён: модуль выключается, данные сохраняются, исправление
  выпускается следующей совместимой миграцией.

## Откат интерфейса

Если после публикации обнаружена ошибка, вернуть предыдущий набор файлов отдельным revert-коммитом и снова выполнить health check. Расширяющую миграцию при этом не откатывать: старый интерфейс продолжает работать с добавленными таблицами и функциями.

Перед revert проверить, что коммит содержит только файлы интерфейса. Не применять `git reset --hard`, не переписывать историю `main` и не включать SQL-миграцию в откат интерфейса.

Если проблема находится в новой функции БД, выпускать следующую совместимую миграцию. Удаление старого RPC допускается только отдельным поздним выпуском после измеренного отсутствия старых клиентов.

## Стоп-условия

Публикация останавливается, если:

- тестовая миграция или статические проверки не прошли;
- отсутствует резервная копия или проверка восстановления;
- production SHA изменился параллельно;
- health check неуспешен;
- новый webhook-адаптер не проверяет подпись либо его секрет отсутствует;
- v87–v89 оказались включены миграцией без отдельного действия владельца;
- клиентский канал допускает отправку без подтверждённого endpoint и согласия;
- требуется откат destructive-миграции.

Слои v92–v97 активируют серверную основу аналитики, истории, отчётов и импорта без отдельного пользовательского переключателя. Откат v92 допускается только пока ни у одной записи не заполнена атрибуция и после удаления v93. Откат v93 допускается только до появления событий в `booking_events`; после этого данные сохраняются, а исправление выпускается новой совместимой миграцией. Откаты v94/v96/v97 предназначены только для изолированной тестовой базы; v97 при этом сохраняет исторические снимки. Откат v95 блокируется после первого импорта.

Телефонный вход v90 активируется только после применения миграции, настройки SMS-провайдера и CAPTCHA в Supabase Auth. До этого кнопки остаются отключёнными, а email/пароль и личный код клиента продолжают работать. Откат v90 блокируется после появления связей `client_accounts.auth_user_id`; в таком состоянии выпускать только совместимое исправление вперёд.

Внешний вход v91 активируется отдельно для каждого Custom OAuth/OIDC-провайдера только после регистрации приложения, сохранения Client Secret в Supabase Auth и проверки связывания на тестовом аккаунте. Публичные флаги в `config.js` включаются последними; до этого кнопки показывают состояние «Не подключён» и не перенаправляют пользователя.

## Узкий выпуск оформления клиентской страницы v118

Workflow `.github/workflows/minuta-v118-safe-release.yml` запускается только вручную и работает только с `supabase-migration-v118.sql`. Старые миграции он не применяет и не изменяет. Все фазы требуют точный 40-символьный SHA, совпадающий с SHA выбранного запуска.

1. `test-v118`: на изолированной test DB выполняет `apply -> integration -> rollback -> reapply`, проверяет защитный маркер базы и сохраняет attestation.
2. `validate-production-v118`: на `main` выполняет только read-only проверку prerequisites, чистого pre-apply состояния и безопасного rollback-файла.
3. После этого создать свежую зашифрованную production-копию на том же SHA.
4. `apply-production-v118`: вручную требует `APPLY_V118_TO_PRODUCTION`, точные IDs успешных test/validation/backup запусков, совпадение SHA и `main`, свежесть доказательств, наличие attestation и проверенный checksum backup-артефакта.
5. `observe-production-v118`: требует ID успешного apply-запуска и выполняет только read-only проверку схемы и публичный health check.

До отдельного ручного запуска `apply-production-v118` workflow ничего в production не изменяет. Для test используется environment `minuta-test`; validation, apply и observation используют защищённый environment `minuta-production`. Любое несовпадение SHA, ветки, project ref, run ID, возраста или артефакта останавливает выпуск.

## Узкий выпуск карточки клиента v119

Workflow `.github/workflows/minuta-v119-safe-release.yml` применяет только `supabase-migration-v119.sql`. Последовательность обязательна: `test-v119` (apply/integration/rollback/reapply на изолированной базе), `validate-production-v119` (read-only), свежий зашифрованный backup на том же SHA, `apply-production-v119` с подтверждением `APPLY_V119_TO_PRODUCTION` и точными run ID, затем `observe-production-v119` (read-only). Откат сохраняет персональные данные и запрещён при активных блокировках онлайн-записи.
