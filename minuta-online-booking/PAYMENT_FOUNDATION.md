# Платёжный фундамент Minuta

Файл `supabase-migration-v47.sql` добавляет платёжный журнал без привязки к конкретному провайдеру. Миграция подготовлена, но сама по себе не включает приём денег.

## Границы доверия

- Браузер никогда не подтверждает оплату и не получает `service_role`.
- Серверный адаптер регистрирует созданную у провайдера операцию через `register_payment_operation`.
- Общий HMAC-webhook сначала проверяется по точному исходному телу и секрету, затем вызывает `process_payment_webhook` с ролью `service_role`; официальный webhook ЮKassa проверяется отдельным контрольным GET, описанным в разделе v87.
- В БД сохраняется SHA-256 тела, но не исходный webhook с персональными или платёжными данными.
- `provider + provider_operation_id` и `provider + provider_event_id` уникальны.
- Повтор одного события возвращает прежний успешный результат. Событие с тем же ID и другим содержимым отклоняется.
- Сумма и валюта webhook должны совпадать с зарегистрированной операцией и суммой предоплаты записи.
- Статус записи вычисляется из платёжного журнала, а не принимается от браузера.

## Подключение провайдера

До развёртывания необходимо выбрать провайдера и реализовать его отдельный адаптер подписи. Шаблон `supabase/functions/payment-webhook/provider-adapter.ts` поддерживает только явно включаемый контракт `generic-hmac-sha256-v1`; неизвестный адаптер завершает запрос без обработки.

Для тестового проекта нужны секреты Edge Function:

- `PAYMENT_WEBHOOK_ADAPTER` — имя проверенного адаптера;
- `PAYMENT_WEBHOOK_SIGNING_SECRET` — отдельный секрет длиной не менее 32 символов;
- `PAYMENT_PROVIDER_ID` — нормализованное имя провайдера;
- стандартные `SUPABASE_URL` и `SUPABASE_SECRET_KEYS`; для старых проектов шаблон временно поддерживает `SUPABASE_SERVICE_ROLE_KEY`.

Значения секретов нельзя помещать в репозиторий, логи, URL или клиентский JavaScript.

## Порядок тестирования

1. Применить v47 только к отдельному тестовому Supabase.
2. Создать тестовую запись с ненулевой предоплатой.
3. Серверной ролью зарегистрировать операцию на точную сумму в копейках.
4. Отправить корректно подписанный `pending`, затем `paid`.
5. Повторить `paid` с тем же event ID — в журнале должна остаться одна запись.
6. Повторить тот же ID с изменённым телом — запрос должен быть отклонён.
7. Проверить неправильную подпись, просроченный timestamp, другую сумму и переход `paid -> pending`.
8. Выполнить ручную корректировку владельцем записи с причиной не короче восьми символов и проверить аудит.
9. Убедиться, что `anon` и обычный `authenticated` не могут вызвать серверные RPC или менять таблицы напрямую.

## Что остаётся после выбора провайдера

- заменить общий HMAC-контракт его официальным алгоритмом подписи;
- реализовать серверное создание операции и безопасную выдачу ссылки/формы оплаты;
- сопоставить реальные типы событий со статусами Minuta;
- определить правила частичного возврата и нескольких платежей;
- зарегистрировать URL Edge Function в кабинете провайдера;
- пройти тестовый платёж и возврат в sandbox провайдера.

Старый RPC `set_booking_payment_status(uuid, text)` сохранён для старых клиентов, но после v47 направляет изменения через новый журнал аудита.

## Слой ЮKassa v87

Миграция `supabase-migration-v87.sql` и функции `yookassa-create-payment`,
`payment-webhook`, `yookassa-refund` подготавливают прямое подключение ЮKassa.
Модуль каждой организации после миграции выключен. Пока владелец его не
включил, новый checkout возвращает сохранённую HTTPS-ссылку старой схемы, если
она есть, и не создаёт операцию у ЮKassa.

### Изоляция организаций

- Настройки находятся в `organization_payment_provider_settings`, а попытки,
  возвраты, события и сверки всегда содержат `organization_id`.
- Финансовый журнал доступен для чтения только владельцу и администратору своей
  организации. Изменить настройки может только владелец.
- Создание платежа принимает `manage_token` и ключ идемпотентности, но сумму,
  валюту, организацию, услугу и контакт клиента получает на сервере из записи.
- Публичный `get_yookassa_payment_capability` по токену управления сообщает
  только доступность checkout и безопасную HTTPS-ссылку. Настройки магазина и
  реквизиты через него не выдаются. Клиент хранит UUID попытки в рамках вкладки,
  а сервер при потере UUID повторно использует открытую попытку той же записи.
- Возврат принимает серверно проверенного пользователя; RPC дополнительно
  подтверждает активную роль владельца или администратора.
- Открытая попытка на одну запись только одна. Несколько частичных возвратов
  резервируют сумму транзакционно и не могут превысить принятую оплату.
- Старые `payments`, `payment_events` и `payment_url` не удаляются. v87 отражает
  итог в прежнем журнале и сохраняет старую ссылку как отключённый fallback.

### Проверка webhook ЮKassa

ЮKassa не подписывает уведомления секретом магазина. Поэтому адаптер
`yookassa-v1` не использует `PAYMENT_WEBHOOK_SIGNING_SECRET`: из входящего тела
он берёт только идентификатор и служебную область, затем обязательно получает
канонический платёж или возврат запросом `GET https://api.yookassa.ru/v3/...`.
До записи события сравниваются идентификаторы Minuta в `metadata`, организация,
окружение, сумма, валюта и тестовый признак платежа. Повтор webhook подавляется
уникальным ключом события.

Тот же endpoint сохраняет прежний generic HMAC-контракт: в режимах
`yookassa-v1` и `hybrid-v1` уведомления с официальной формой ЮKassa идут через
контрольный GET, а остальные запросы обязаны пройти прежние timestamp и HMAC
проверки. Для работы обоих каналов рядом сохраняются
`PAYMENT_WEBHOOK_SIGNING_SECRET` и `PAYMENT_PROVIDER_ID`; события двух форматов
попадают в свои идемпотентные журналы и не подтверждаются по форме тела.

### Секреты Edge Functions

Для нескольких организаций рекомендуется один секрет `YOOKASSA_ACCOUNTS_JSON`:
ключи верхнего уровня — UUID организаций, внутри отдельные объекты `test` и
`production` с полями `shop_id` и `secret_key`. Этот JSON существует только в
секретах окружения Edge Functions и никогда не возвращается клиенту.

Для одного магазина допускается отдельная конфигурация, жёстко привязанная к
одной организации:

- `YOOKASSA_ORGANIZATION_ID`;
- `YOOKASSA_TEST_SHOP_ID` и `YOOKASSA_TEST_SECRET_KEY`;
- `YOOKASSA_SHOP_ID` и `YOOKASSA_SECRET_KEY` для production;
- `YOOKASSA_RETURN_URL` — фиксированный HTTPS-адрес возврата после оплаты;
- `PAYMENT_WEBHOOK_ADAPTER=hybrid-v1` (значение `yookassa-v1` также сохраняет
  совместимость с прежним HMAC-каналом);
- `SUPABASE_URL`, `SUPABASE_ANON_KEY` и серверный ключ Supabase.

Глобальные реквизиты нельзя использовать без `YOOKASSA_ORGANIZATION_ID`: это
предотвращает случайное направление платежа другой организации в общий магазин.

### Фискализация

Фискализация выключена по умолчанию. При включении владелец обязан явно задать
СНО, код НДС и признак способа расчёта. Edge Function формирует одну позицию
`service` на точную сумму предоплаты или возврата и использует телефон клиента
из записи. Юридически корректные значения этих полей организация выбирает со
своим бухгалтером; приложение их не угадывает. В БД СНО хранится как внутренний
код (`osn`, `usn_income`, `usn_income_outcome`, `esn`, `patent`), а Edge Function
строго переводит его в официальный числовой `receipt.tax_system_code`: 1, 2,
3, 5 или 6 соответственно. Устаревший код 4 (ЕНВД) в интерфейсе недоступен.
Код НДС проверяется в полном поддерживаемом диапазоне 1–12.

### Перед активацией

1. Применить v87 сначала в тестовой базе.
2. Развернуть три Edge Function и добавить секреты тестового магазина.
3. В кабинете ЮKassa зарегистрировать `payment.waiting_for_capture`,
   `payment.succeeded`, `payment.canceled` и `refund.succeeded` на URL
   `payment-webhook`.
4. Проверить повтор создания с тем же ключом, поддельный webhook, обязательный
   контрольный GET, успешную оплату, полный и несколько частичных возвратов.
5. Проверить чек прихода и чек возврата, если фискализация включена.
6. Только затем добавить production-реквизиты и отдельно включить организацию.

v87 не содержит значения Shop ID или Secret Key и сам по себе не включает
приём реальных денег.

Полный `supabase-migration-v87-rollback.sql` разрешён только до появления первой
платёжной попытки. После начала работы откат не должен удалять финансовый журнал:
организацию нужно выключить настройкой и выпускать исправляющую миграцию вперёд.
