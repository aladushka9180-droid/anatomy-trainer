# Регламент проекта «Сайт Онлайн записи»

Этот файл действует для всего репозитория и всех вложенных каталогов. Более близкий `AGENTS.md` может уточнять правила для своей части проекта, но не отменяет требования по изоляции параллельной работы и защите `main`.

## Параллельные сессии

- Несколько сессий могут работать одновременно, если каждая изменяющая код задача использует отдельный Git worktree и отдельную ветку `codex/<краткая-задача>`.
- Одна сессия — один worktree — одна ветка. Нельзя использовать одну ветку или один рабочий каталог в двух сессиях.
- Общую локальную копию с незакоммиченными изменениями не использовать для новой реализации. Она предназначена для просмотра, ручной проверки и интеграции.
- Задачи только на чтение можно выполнять без отдельного worktree, если они не меняют файлы, индекс Git, зависимости, сборочные артефакты и внешнее состояние.

## Начало задачи

1. Определить корень репозитория, текущую ветку и состояние через `git rev-parse --show-toplevel`, `git branch --show-current` и `git status --short`.
2. Выполнить `git fetch origin main` и брать основу новой ветки из свежего `origin/main`, если пользователь явно не указал другую основу.
3. Проверить `git worktree list --porcelain`. Если доступны инструменты задач Codex, также проверить активные задачи этого проекта и их области работы.
4. До правок зафиксировать для себя точный список файлов и подсистем текущей задачи. Не захватывать соседние функции «заодно».
5. Если другая активная сессия уже меняет те же файлы или тот же сценарий, не вести параллельную запись в них. Перейти к независимой части, ограничиться анализом либо дождаться интеграции первой ветки и обновить свою основу.

## Работа и агенты

- Индексировать и коммитить только файлы текущей задачи. Незнакомые изменения считать чужими и не исправлять, не удалять и не включать в коммит.
- Не использовать `git reset --hard`, force-push, удаление чужих веток/worktree и команды, которые могут стереть незакоммиченную работу.
- Субагентов безопасно запускать параллельно для анализа, поиска, ревью и проверок. Параллельные правки разрешены только при заранее разделённых, непересекающихся наборах файлов; итоговую интеграцию выполняет одна основная сессия.
- При необходимости изменить общий файл назначить одну сессию его владельцем. Остальные передают ей рекомендации или отдельные коммиты и не редактируют этот файл одновременно.
- Перед коммитом проверить `git status --short` и `git diff --check`, затем выполнить только проверки, требуемые ближайшим `AGENTS.md` и характером изменения.

## Общие номера и ресурсы

- Номера миграций, версии service worker/кэша, версии релиза и другие монотонные идентификаторы назначать после сверки со свежим `origin/main`.
- Перед интеграцией повторно проверять уникальность таких номеров. При коллизии перенумеровать текущую ветку, не переписывая уже опубликованную историю.
- Секреты, локальные `.env`, дампы, временные архивы и пользовательские материалы не переносить между worktree и не добавлять в Git без прямого запроса.

## Интеграция и публикация

- В каждый момент времени только одна сессия является владельцем выпуска для этого репозитория. Только она может отправлять изменения в `main`, запускать production-деплой и применять production-миграции.
- Рабочие сессии завершают задачу отдельным коммитом в своей ветке и передают владельцу выпуска SHA, список файлов, выполненные проверки и необходимые шаги публикации.
- Владелец выпуска перед интеграцией выполняет `git fetch origin main`, переносит только целевые коммиты через rebase/cherry-pick/merge и сохраняет более новые изменения из `main` при разрешении конфликтов.
- Отправлять изменения в `main` только обычным push без force. Если push отклонён, снова получить свежий `origin/main`, интегрировать изменения и повторить проверки; чужую историю не перезаписывать.
- Production-операции выполнять последовательно. Миграции применять только после выполнения проектных требований к свежему бекапу и безопасному откату.
- Не утверждать, что функция опубликована или миграция применена, пока это не подтверждено соответствующим удалённым состоянием или успешным запуском.

## Координатор и очередь конфликтующих задач

- Владелец выпуска одновременно является координатором всех задач, которые могут изменить `main`, production или общие файлы. Сообщения между сессиями являются способом координации, но не заменяют отдельные worktree, ветки и правило единственного отправителя в `main`.
- Перед началом production-операции координатор проверяет активные задачи проекта. Задачам, которые работают с `main`, production либо пересекающимися файлами, он отправляет команду остановиться до записи, коммита, push или внешнего изменения и сохраняет их идентификаторы в порядке возобновления.
- Остановленная задача обязана подтвердить остановку, не начинать новые изменяющие команды и не возобновляться по времени, догадке или собственному решению. Незавершённую безопасную операцию чтения можно закончить; изменяющую операцию нельзя продолжать до отдельной команды координатора.
- Пока действует блокировка координатора, только он может интегрировать изменения, отправлять их в `main`, выполнять production-деплой и применять миграции. Другие задачи могут выполнять независимый анализ или готовить коммиты только в собственных ветках, если координатор явно это разрешил.
- После успешного завершения своей операции координатор обязан возобновить сохранённые задачи строго по одной. В сообщении каждой задаче он передаёт текущий SHA `origin/main`, разрешённую область работы и требование заново выполнить `git fetch origin main` и обновить основу перед любыми изменениями.
- После возобновления одной задачи координатор ждёт её завершения, блокера либо передачи отдельного коммита владельцу выпуска. Следующую задачу из очереди нельзя запускать раньше, если их файлы, ветки или production-действия могут пересечься.
- Если операция координатора завершилась ошибкой, состояние production не подтверждено или безопасная интеграция невозможна, задачи автоматически не возобновлять. Координатор сообщает пользователю причину и сохраняет очередь остановленных задач для последующего явного продолжения.
- Если координатор сам завершается до обработки очереди, он до финального ответа обязан передать очередь другой активной задаче-координатору либо явно сообщить пользователю, какие задачи остаются остановленными.
- При повторном конфликте задача снова возвращается в очередь. Запрещено обходить очередь force-push, перезаписью чужой ветки, использованием устаревшего worktree или публикацией поверх непроверенного `origin/main`.

## Завершение

- После интеграции удалять только собственный временный worktree и только когда его коммиты сохранены в ветке или `main`.
- Не удалять чужие worktree, ветки и незнакомые временные каталоги.
- Эти инструкции загружаются при старте новой сессии. Уже открытой сессии нужно явно перечитать корневой `AGENTS.md` либо начать новую задачу, чтобы гарантированно получить обновлённый регламент.
